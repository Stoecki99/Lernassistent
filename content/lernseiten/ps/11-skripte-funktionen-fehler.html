PS · Teil 4 · Skripte

Skripte, Funktionen und Fehler

Lea tippt jeden Montag dieselben drei Befehle, um alte Logdateien zu finden. Das geht besser: Sie speichert die Befehle als Skript, gibt ihm Parameter und baut daraus eigene Befehle. Und wenn etwas schiefgeht, liest sie die rote Meldung wie ein Profi und fängt Fehler gezielt ab.

Lernziele

  • Du speicherst Befehle als Skript .ps1 und startest es mit .\name.ps1.
  • Du erklärst, was die Ausführungsrichtlinie tut und was nicht, und setzt sie für dich selbst.
  • Du gibst Skripten und Funktionen Parameter mit Typ und Standardwert.
  • Du schreibst eine eigene Funktion in der Form Verb-Nomen.
  • Du unterscheidest abbrechende und nicht abbrechende Fehler und fängst sie mit try/catch ab.
  • Du liest eine Fehlermeldung von PowerShell 7 und findest Befehl, Zeile und Ursache.

Vom Zettel zum Rezept

Bisher hast du jeden Befehl neu getippt. Das ist wie Kochen ohne Rezept: Du musst dir jedes Mal merken, was in welcher Reihenfolge kommt. Ein Skript ist das aufgeschriebene Rezept. Du schreibst die Befehle einmal in eine Textdatei und lässt PowerShell sie später Zeile für Zeile abarbeiten, so oft du willst.

Ein gutes Rezept hat Lücken für Dinge, die sich ändern: «für 4 Personen». Diese Lücken heissen Parameter. Ein Teilrezept, das du immer wieder brauchst («Grundteig»), bekommt einen eigenen Namen: Das ist eine Funktion. Und wenn in der Küche etwas schiefgeht, brauchst du einen Plan B: die Fehlerbehandlung.

Skript.\logbericht.ps1

Eine Textdatei mit der Endung .ps1 voller Befehle. Das Rezept.

Parameterparam([int]$Tage = 30)

Eine Lücke im Rezept, die du beim Start füllst. Ohne Angabe gilt der Standardwert.

Funktionfunction Get-AlteLogdatei { }

Ein eigener Befehl mit Namen. Das Teilrezept, das du immer wieder aufrufst.

Fehlerbehandlungtry { } catch { }

Plan B: Geht im try-Teil etwas schief, springt PowerShell in den catch-Teil.

Kurz üben: Welcher Baustein ist das?

Schritt 1 · Die Skriptdatei

Ein Skript schreiben und starten

Eine Textdatei mit der Endung .ps1

Ein Skript ist eine gewöhnliche Textdatei. Ihr Name endet auf .ps1. Darin stehen Befehle, je einer pro Zeile, genau so, wie du sie in der Konsole tippen würdest. Leas erstes Skript heisst begruessung.ps1 und hat zwei Zeilen:

Datei begruessung.ps1

param([string]$Name = 'Lea')
"Guten Morgen, $Name!"

Schreiben kannst du Skripte mit jedem Texteditor, sogar mit dem Windows-Editor. Viel bequemer ist Visual Studio Code mit der Erweiterung PowerShell von Microsoft: Sie färbt den Code, vervollständigt Befehle mit Tab, unterstreicht Tippfehler, bevor du startest, und führt das Skript mit F5 aus. Beides ist kostenlos.

Unterschied 5.1: Windows PowerShell 5.1 bringt den Editor «Windows PowerShell ISE» mit. Er kennt nur 5.1, nicht PowerShell 7, und Microsoft entwickelt ihn nicht weiter. Nimm darum Visual Studio Code.

Starten mit .\

Ein Skript startest du über seinen Pfad. Liegt es im aktuellen Ordner, schreibst du .\ davor. Der Punkt heisst «hier», der Backslash trennt Ordner und Datei. .\begruessung.ps1 heisst also «die Datei begruessung.ps1 genau hier».


      
Ohne .\ findet PowerShell das Skript nicht, obwohl es direkt vor ihm liegt:

      
PS C:\Users\lea> begruessung.ps1
begruessung.ps1: The term 'begruessung.ps1' is not recognized as a name of a cmdlet, function, script file, or executable program.
Check the spelling of the name, or if a path was included, verify that the path is correct and try again.

      
Auf Deutsch: «Einen Befehl mit diesem Namen kenne ich nicht.» Das ist Absicht und eine Schutzmassnahme. PowerShell sucht Befehle von sich aus nicht im aktuellen Ordner. Sonst könnte ein Programm namens ping.exe, das jemand in deinen Downloads versteckt, statt des echten ping laufen. Mit .\ sagst du ausdrücklich: «Ja, ich meine diese Datei.» Echtes pwsh zeigt darunter zusätzlich einen Vorschlag, es mit .\begruessung.ps1 zu versuchen.

      
Parameter schreibst du wie bei einem Cmdlet hinter den Namen:

      

      
Doppelklick: Ein Doppelklick auf eine .ps1-Datei im Explorer startet sie nicht, sondern öffnet sie meist im Editor. Auch das ist eine Schutzmassnahme. Starte Skripte in der Konsole oder in Visual Studio Code.

    


    

      
Die Ausführungsrichtlinie

      
Vielleicht kennst du das Schild «Betreten auf eigene Gefahr» an einer Baustelle. Es hält niemanden mit Gewalt ab, aber es verhindert, dass jemand aus Versehen hineinläuft. Genau so arbeitet die Ausführungsrichtlinie (englisch execution policy) unter Windows: Sie legt fest, ob und welche Skripte starten dürfen. Mit Get-ExecutionPolicy fragst du sie ab.

      

      

        

          Die wichtigsten Richtlinien (Quelle: about_Execution_Policies)
          
RichtlinieWas ist erlaubt?

          
            
Restrictedeinzelne Befehle in der Konsole, aber keine Skripte. Gilt auf Windows-Clients, wenn nirgends etwas eingestellt ist.

            
RemoteSignedeigene Skripte vom eigenen Rechner laufen. Skripte aus dem Internet (Download, Mail-Anhang, Chat) brauchen eine digitale Signatur. Die übliche Einstellung.

            
AllSignednur signierte Skripte, auch die eigenen

            
Unrestrictedalle Skripte; bei Skripten aus dem Internet fragt PowerShell nach

            
Bypassnichts wird blockiert, keine Warnung. Gedacht für Programme, die PowerShell einbauen.

          
        

      

      
Die Richtlinie kann an mehreren Orten (Bereichen, englisch scopes) stehen. Get-ExecutionPolicy -List zeigt alle. Der oberste Eintrag, der nicht Undefined ist, gewinnt. Auf Leas Rechner steht RemoteSigned für den ganzen Computer (LocalMachine):

      

      
Laufen auf deinem Rechner keine Skripte, stellst du RemoteSigned nur für dich ein. Dafür brauchst du keine Adminrechte:

      
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

      
Ohne -Scope würde PowerShell den Bereich LocalMachine ändern, und das geht nur in einer Konsole «als Administrator». Den Bereich Process vergisst PowerShell beim Schliessen des Fensters. Damit kannst du gefahrlos ausprobieren, was Restricted bewirkt:

      

      
Auf Deutsch: «Die Datei kann nicht geladen werden, weil das Ausführen von Skripten auf diesem System deaktiviert ist.» Danach stellt Lea für diese Sitzung wieder RemoteSigned ein, und das Skript läuft.

      
Keine Sicherheitsgrenze: Microsoft sagt es selbst: Die Ausführungsrichtlinie ist ein Sicherheitsgurt gegen Versehen, kein Schloss gegen Angreifer. Wer will, kopiert den Inhalt eines Skripts einfach in die Konsole. Stell sie darum nicht auf Unrestricted oder Bypass, «damit es endlich geht». RemoteSigned reicht für eigene Skripte.

      
Unterschied 5.1: Windows PowerShell 5.1 und PowerShell 7 speichern ihre Richtlinien getrennt (5.1 in der Registry, 7 in der Datei powershell.config.json). Was du in der einen einstellst, gilt nicht für die andere. Ausserhalb von Windows (macOS, Linux) gilt fest Unrestricted, und das lässt sich nicht ändern.

    


    

      
Kommentare: Notizen für Menschen

      
Alles nach einem # bis zum Zeilenende ist ein Kommentar. PowerShell überliest ihn. Für längere Notizen gibt es den Block-Kommentar von <# bis #>, er darf über viele Zeilen gehen. Schreib in Kommentare, warum etwas so ist. Was der Code tut, sieht man im Code.

      
<#
  logbericht.ps1 · Lea, Informatik Wolkenried
  Zählt Dateien, die älter als eine bestimmte Anzahl Tage sind.
#>
$Tage = 30   # Archiv-Regel der Gemeinde: 30 Tage

      
Merke: Block-Kommentare lassen sich nicht verschachteln: Der erste #> beendet den Kommentar. In Anführungszeichen ist # kein Kommentar: 'Text # kein Kommentar' gibt den ganzen Text aus.

    

  


  
  

    Schritt 2 · Vom Befehl zum Skript mit Parametern
    
Leas Montagsbefehl wird ein Skript

    
Lea baut ihr Skript in fünf kleinen Schritten. Klick dich mit «Weiter» durch. Fahre über ein unterstrichenes Satzstück: Der passende Teil leuchtet auf. Unter jedem Skript siehst du, was der Simulator beim Start ausgibt.

    


    

      
param(): Typ, Name, Standardwert

      
Im Block param( ) stehen die Parameter, durch Komma getrennt. Jeder hat bis zu drei Teile:

      
param(
  [string]$Ordner = 'Logs',
  [int]$Tage = 30
)

      
    
        
  • Typ in eckigen Klammern: [string] für Text, [int] für ganze Zahlen. Der Typ ist freiwillig, aber er schützt dich vor Unsinn.
    • 
        
  • Name mit $: Im Skript ist er eine Variable, beim Start ein Parameter -Ordner.
    • 
        
  • Standardwert nach =: Gibst du den Parameter nicht an, gilt er.
    • 
      

      
param( ) muss die erste Anweisung im Skript sein. Davor dürfen nur Kommentare stehen. Beim Start kannst du die Parameter benannt in beliebiger Reihenfolge oder ohne Namen in der Reihenfolge von param( ) angeben:

      

      
Und wenn Lea statt einer Zahl ein Wort eintippt? Dann greift der Typ [int], und das Skript startet gar nicht erst:

      

      
Auf Deutsch: «Den Wert "zehn" kann ich nicht in eine ganze Zahl (System.Int32) umwandeln.» Besser eine klare Meldung am Anfang als ein Skript, das mit Unsinn weiterrechnet.

      
Ausblick: Mit [Parameter(Mandatory)] vor dem Typ wird ein Parameter zur Pflicht. Fehlt er beim Start, fragt PowerShell in der Konsole nach dem Wert. Mehr dazu in about_Functions_Advanced_Parameters.

    

  


  
  

    Schritt 3 · Eigene Befehle
    
Funktionen: dein eigenes Cmdlet

    
Eine Funktion ist ein Stück Code mit einem Namen. Du schreibst function, den Namen und in geschweiften Klammern den Inhalt. Der Parameterblock steht als Erstes in den Klammern. Danach rufst du die Funktion auf wie jedes Cmdlet. Gib ihr einen Namen in der Form Verb-Nomen mit einem genehmigten Verb (Station 02), dann versteht jeder sofort, was sie tut.

    
function Get-AlteLogdatei {
  param(
    [string]$Ordner = 'Logs',
    [int]$Tage = 30
  )
  $grenze = (Get-Date).AddDays(-$Tage)
  Get-ChildItem -Path $Ordner -File | Where-Object LastWriteTime -lt $grenze
}

Get-AlteLogdatei -Tage 90 | Select-Object -ExpandProperty Name

    

    
Die Funktion gibt Dateiobjekte aus. Darum kannst du sie weiter in die Pipeline schicken, hier an Select-Object. Älter als 90 Tage sind nur zwei Logdateien.


    

      
Ausgabe statt return

      
In vielen Programmiersprachen gibt eine Funktion nur das zurück, was nach return steht. In PowerShell ist das anders: Alles, was in der Funktion eine Ausgabe erzeugt, kommt heraus. Jeder Text, jede Zahl, jedes Objekt, das nicht in einer Variable landet. return beendet die Funktion nur früher.

      
function Test-Zahl { 'eins'; return 'zwei'; 'drei' }
Test-Zahl

      

      
eins kommt heraus, obwohl kein return davor steht. drei fehlt, weil return die Funktion vorher beendet. Schreib darum einfach das hin, was herauskommen soll. return brauchst du nur, wenn du früher aufhören willst.

    


    

      
Aufrufen wie ein Cmdlet

      
function Get-Gruss { param([string]$Name = 'Lea') "Hallo $Name" }

      

      
Merke: Im Skript muss eine Funktion oben stehen, bevor du sie aufrufst. PowerShell liest das Skript von oben nach unten und kennt sie sonst noch nicht.

    

  


  
  

    Schritt 4 · Wenn etwas schiefgeht
    
Zwei Arten von Fehlern

    
Denk an eine Ampel. Bei gelbem Blinklicht fährst du vorsichtig weiter. Bei Rot bleibst du stehen. PowerShell kennt genau diese zwei Arten von Fehlern.

    

      
nicht abbrechendgelb blinkend
Der Befehl meldet das Problem in Rot und macht mit dem Rest weiter. Typisch: eine von mehreren Dateien fehlt.

      
abbrechendrot
Die Anweisung bricht ab. Typisch: ein unbekannter Befehl, ein falscher Typ. Bei throw und -ErrorAction Stop hält sogar das ganze Skript an, wenn kein catch den Fehler fängt.

-ErrorAction: wie soll der Befehl reagieren?

      
Jedes Cmdlet hat den gemeinsamen Parameter -ErrorAction (kurz -ea). Er sagt, was bei einem nicht abbrechenden Fehler passieren soll:

SilentlyContinuekeine Meldung, weitermachen. Der Fehler landet trotzdem in $Error.

            
Ignorekeine Meldung, weitermachen, nicht in $Error

            
StopMeldung und anhalten: Aus dem gelben wird ein roter Fehler. Den kann catch abfangen.

Vorsicht mit SilentlyContinue: Wer alle Fehler verschluckt, merkt nicht, dass etwas nicht klappt. Nimm es nur, wenn ein Fehler wirklich egal ist, zum Beispiel «Datei löschen, falls es sie gibt».

    


    

      
try, catch, finally: Plan B

      
Was im try-Block steht, versucht PowerShell. Tritt dort ein abbrechender Fehler auf, springt es sofort in den catch-Block. Der Rest von try wird übersprungen. Der finally-Block läuft am Schluss immer, mit oder ohne Fehler. Er ist freiwillig und gut zum Aufräumen.

      
try {
  'Ich lese die Datei ...'
  Get-Content -Path Logs\fehlt.log -ErrorAction Stop
  'Gelesen.'
}
catch {
  "Fehler: $($_.Exception.Message)"
}
finally {
  'Fertig.'
}

      

      
Im catch-Block steht $_ für den Fehler, den PowerShell gerade gefangen hat. $_.Exception.Message ist nur der Text der Meldung, ohne rote Farbe und ohne Befehlsname. Den kannst du in eine eigene, freundliche Meldung einbauen.

      
Die wichtigste Falle: catch fängt nur abbrechende Fehler. Ohne -ErrorAction Stop ist «Datei fehlt» bei Get-Content nur gelb blinkend. PowerShell zeigt die rote Meldung, macht im try-Block weiter, und catch läuft nie:

      

      
Abbrechend sind dagegen schon von sich aus: throw 'Text', ein Befehl, den es nicht gibt, und ein Wert, der nicht in den Typ passt ([int]'zehn'). Die fängt catch auch ohne -ErrorAction Stop.

    


    

      
$Error: das Fehlertagebuch

      
PowerShell merkt sich jeden Fehler der Sitzung in der automatischen Variable $Error, den neusten zuoberst. $Error[0] ist also der letzte Fehler, auch wenn du ihn mit SilentlyContinue versteckt oder mit catch gefangen hast.

      

      
Unterschied 5.1: Nur PowerShell 7 hat das Cmdlet Get-Error, das den letzten Fehler mit allen Einzelheiten zeigt. Windows PowerShell 5.1 kennt es nicht.

    Typische Fehler
    
Die häufigsten Stolpersteine

    
Skript ohne .\: logbericht.ps1 ergibt «is not recognized». PowerShell sucht von sich aus nicht im aktuellen Ordner. Richtig: .\logbericht.ps1.

    
Leerzeichen im Pfad: .\Meine Skripte\hallo.ps1 zerfällt am Leerzeichen, PowerShell sucht einen Befehl .\Meine. Nur Anführungszeichen helfen auch nicht, dann ist es bloss ein Text, den PowerShell ausgibt. Richtig ist der Aufrufoperator & vor dem Pfad in Anführungszeichen:
      
PS C:\Users\lea> .\Meine Skripte\hallo.ps1
.\Meine: The term '.\Meine' is not recognized as a name of a cmdlet, function, script file, or executable program.
Check the spelling of the name, or if a path was included, verify that the path is correct and try again.
PS C:\Users\lea> & '.\Meine Skripte\hallo.ps1'
Hallo von Lea

    
try/catch ohne -ErrorAction Stop: Fehlt bei Get-Content oder Get-ChildItem die Datei, ist das ein nicht abbrechender Fehler. catch bleibt stumm, das Skript rechnet mit leeren Werten weiter («0 Zeilen»). Schreib -ErrorAction Stop an jeden Befehl im try-Block, dessen Fehler du fangen willst.

    
Funktion mit Klammern und Komma aufrufen: Get-Gruss('Tom', 3) sieht aus wie in anderen Sprachen, ist in PowerShell aber falsch. PowerShell übergibt ('Tom', 3) als eine Liste an den ersten Parameter. Richtig: Get-Gruss -Name Tom -Anzahl 3, mit Leerzeichen, ohne Klammern, ohne Komma.

    
Funktion zu spät definiert: Rufst du im Skript eine Funktion auf, bevor ihr function-Block kommt, meldet PowerShell «The term '…' is not recognized». Funktionen gehören nach oben, direkt unter param( ).

    
param() nicht zuoberst: Steht vor param( ) schon ein Befehl, erkennt PowerShell den Block nicht mehr als Parameter. Echtes pwsh 7.6 hält param dann für einen unbekannten Befehl, und dein Parameter wird nicht übernommen:
      
PS C:\Users\lea> .\spaet.ps1 -Tage 60
Start
param: C:\Users\lea\spaet.ps1:2
Line |
   2 |  param([int]$Tage = 30)
     |  ~~~~~
     | The term 'param' is not recognized as a name of a cmdlet, function, script file, or executable program. Check
     | the spelling of the name, or if a path was included, verify that the path is correct and try again.
Tage: 30

      Nur Kommentare dürfen vor param( ) stehen.

    
Funktion aus einem Skript fehlt danach: Ein Skript läuft in seinem eigenen Bereich. Eine Funktion, die werkzeuge.ps1 definiert, kennt die Konsole nach dem Start mit .\werkzeuge.ps1 nicht mehr. Willst du sie behalten, startest du das Skript mit einem Punkt und Leerzeichen davor: . .\werkzeuge.ps1 (englisch dot sourcing). Der Simulator vereinfacht das: Dort bleibt die Funktion auch ohne Punkt bekannt.

    
Richtlinie «aufmachen», bis es geht: Set-ExecutionPolicy Unrestricted oder Bypass ist nicht nötig. Für eigene Skripte reicht Set-ExecutionPolicy RemoteSigned -Scope CurrentUser.

    
Nur die erste Zeile lesen: Die erste Zeile einer Meldung nennt Befehl und Ort, die Ursache steht ganz unten. Lies immer bis zur letzten Zeile.

    
Umlaute in Skripten 5.1: Windows PowerShell 5.1 liest Skripte ohne BOM (unsichtbare Kennung am Dateianfang) als ANSI. Aus «älter» wird dann «Ã¤lter». Speichere Skripte für 5.1 als «UTF-8 with BOM» (in Visual Studio Code unten rechts). PowerShell 7 liest beides richtig.

  • Ein Skript ist eine Textdatei .ps1. Im aktuellen Ordner startest du es mit .\ davor.
    • 
      
  • Die Ausführungsrichtlinie schützt vor Versehen, nicht vor Angreifern. RemoteSigned für dich: -Scope CurrentUser.
    • 
      
  • param( ) steht zuoberst. Typ schützt vor Unsinn, Standardwert gilt ohne Angabe.
    • 
      
  • Eine Funktion heisst Verb-Nomen und gibt alles aus, was in ihr eine Ausgabe erzeugt. return beendet sie nur.
    • 
      
  • catch fängt nur abbrechende Fehler. Für «Datei fehlt» braucht es -ErrorAction Stop.
    • 
      
  • Fehlermeldung von unten lesen: Ursache, dann Zeile und Unterstreichung, dann Befehl.

Unterschiede zu Windows PowerShell 5.1

      
    
        
  • Fehleransicht: 7 zeigt die kurze ConciseView mit Line |. 5.1 zeigt die lange Ansicht mit «In Zeile … Zeichen …», CategoryInfo und FullyQualifiedErrorId, auf deutschem Windows in Deutsch.
    • 
        
  • Get-Error gibt es nur in 7.
    • 
        
  • Ausführungsrichtlinien von 5.1 (Registry) und 7 (powershell.config.json) sind getrennt.
    • 
        
  • 5.1 liest Skripte ohne BOM als ANSI: Umlaute gehen kaputt. Speichere sie als UTF-8 mit BOM.
    • 
        
  • Editor: Die ISE gibt es nur für 5.1. Für 7 nimmst du Visual Studio Code mit der PowerShell-Erweiterung.
