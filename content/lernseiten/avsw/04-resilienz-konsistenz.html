Resilienz und Konsistenz

In einem verteilten System fällt immer irgendwo etwas aus: ein Netzwerk, ein Pod, ein Fremddienst. Hier lernst du die Muster, mit denen ein System trotzdem weiterläuft (Timeout, Retry, Circuit Breaker, Bulkhead, Fallback), und die Muster, mit denen die Daten über mehrere Dienste stimmig bleiben (CAP, eventual consistency, Saga, Outbox, CQRS). Am Schluss modellierst du eine Reisebuchung als Saga mit Kompensation.

Schritt 0 · Ohne Vorwissen

Die fünf Bausteine dieser Station

Ein verteiltes System besteht aus vielen Diensten, die über ein Netzwerk miteinander reden. Ein Monolith fällt ganz oder gar nicht aus. Ein verteiltes System fällt teilweise aus, und genau das macht es schwierig. Zwei Fragen begleiten dich durch die ganze Station: Läuft das System weiter, wenn ein Teil hängt? Und stimmen die Daten noch, wenn ein Schritt in der Mitte scheitert?

Teilausfall = eine Kasse zuZahlung hängt, Suche läuft

Im Supermarkt fällt eine Kasse aus, die anderen arbeiten weiter. Im verteilten System hängt ein Dienst, der Rest läuft, wenn man ihn richtig schützt.

Resilienz = SicherungskastenTimeout, Circuit Breaker

Der Sicherungskasten trennt einen defekten Stromkreis ab, damit nicht das ganze Haus brennt. Resilienzmuster trennen einen kranken Dienst ab.

Timeout = nicht ewig wartennach 2 s abbrechen

Am Telefon legst du nach einer Minute Warteschleife auf. Ein Dienst, der auf eine Antwort wartet, braucht dieselbe Grenze.

Konsistenz = alle sehen dasselbeKontostand in Zürich = Genf

Jede Filiale einer Bank soll denselben Kontostand zeigen. Bei Kopien auf mehreren Servern ist das nicht gratis.

Kompensation = StornoHotel buchen → Hotel stornieren

Eine Buchung über drei Firmen kannst du nicht zurückspulen. Du machst sie mit einer Gegenbuchung rückgängig, wie ein Storno auf der Kreditkarte.

Kurz üben: Resilienz- oder Konsistenzproblem?

Frag dich: Geht es darum, dass etwas hängt oder ausfällt (Resilienz)? Oder darum, dass Daten nicht zusammenpassen (Konsistenz)?

Schritt 3 · Resilienzmuster

Teilausfälle eingrenzen

Die acht Irrtümer über verteilte Systeme

Die Fallacies of Distributed Computing sind acht Annahmen, die Entwicklerinnen gern stillschweigend treffen. Alle acht sind falsch. Jede Resilienz-Technik dieser Station antwortet auf mindestens einen Irrtum.

1 · Das Netz ist zuverlässig

Pakete gehen verloren, Verbindungen reissen. Folge: Timeout und Retry.

2 · Die Latenz ist null

Ein Aufruf Zürich–Frankfurt kostet Millisekunden, zehn Aufrufe hintereinander summieren sich.

3 · Die Bandbreite ist unendlich

Ein Video-Streamingdienst merkt das zur Hauptsendezeit. Folge: Caching, Kompression.

4 · Das Netz ist sicher

Auch interner Verkehr kann mitgelesen werden. Folge: TLS, mTLS.

5 · Die Topologie ändert sich nicht

Pods kommen und gehen, IP-Adressen wechseln. Folge: Service Discovery.

6 · Es gibt einen Administrator

Bank, Zahlungsanbieter und Cloud haben je eigene Teams und Wartungsfenster.

7 · Transport kostet nichts

Serialisieren, Verschlüsseln und Datenverkehr in der Cloud kosten Zeit und Geld.

8 · Das Netz ist homogen

Mobile Apps, alte Systeme und neue Dienste sprechen verschiedene Protokolle.

Kaskadenausfall: wie ein langsamer Dienst alles mitreisst

Ein Spital-Portal, ein Webshop oder ein Ticketshop: Das Muster ist immer gleich. Jeder Dienst hat nur eine begrenzte Zahl Threads (Arbeiter). Wartet ein Thread ohne Grenze auf einen langsamen Partner, ist er blockiert. Sind alle blockiert, antwortet der Dienst gar nicht mehr, und seine Aufrufer warten ihrerseits. Spiele beide Varianten ab und vergleiche.

Timeout: die wichtigste Grenze

Ein Timeout begrenzt, wie lange ein Aufruf dauern darf. Ohne Timeout wartet ein HTTP-Client in vielen Bibliotheken unendlich lang. Unterscheide zwei Werte: den Connect-Timeout (Verbindung aufbauen, kurz, etwa 1 s) und den Read-Timeout (auf die Antwort warten, etwa 2 s). Wähle den Wert anhand gemessener Antwortzeiten, zum Beispiel etwas über dem 99. Perzentil.

@Bean
RestClient zahlungRest(RestClient.Builder builder) {
  var factory = new SimpleClientHttpRequestFactory();
  factory.setConnectTimeout(Duration.ofSeconds(1));   // Verbindung aufbauen
  factory.setReadTimeout(Duration.ofSeconds(2));      // auf die Antwort warten
  return builder.baseUrl("http://zahlung:8080")
      .requestFactory(factory)
      .build();
}

Falle Timeout-Budget: Das Gateway bricht nach 3 s ab, der Bestellservice wartet aber 5 s auf die Zahlung. Dann arbeitet der Bestellservice noch, obwohl niemand mehr auf die Antwort wartet. Innere Timeouts (inklusive aller Retries) müssen kürzer sein als äussere.

Retry mit exponentiellem Backoff und Jitter

Viele Fehler sind vorübergehend: ein Pod startet neu, ein Paket geht verloren. Ein zweiter Versuch klappt dann oft. Zwei Regeln machen Retries sicher. Backoff: Warte nach jedem Fehlversuch länger, damit sich der Partner erholen kann. Jitter: Würfle die Wartezeit, damit nicht 10'000 Clients im selben Moment erneut anklopfen (thundering herd).

$$t_n = \min\left(t_{\max},\; t_0 \cdot 2^{\,n}\right), \qquad \text{Wartezeit}_n = \text{zufällig in } [0,\; t_n]$$

Mit \(t_0 = 200\) ms ergibt das die Obergrenzen 200, 400, 800, 1600 ms. Die Variante «zufällig zwischen 0 und Obergrenze» heisst Full Jitter. Wiederhole nur Fehler, die vorübergehend sein können: Timeout, Verbindungsfehler, 502, 503, 504 und 429. Ein 400 (Anfrage falsch) oder 404 wird beim zweiten Mal nicht richtiger.

async function mitRetry<T>(
  aufruf: (signal: AbortSignal) => Promise<T>,
  versuche = 4, basisMs = 200, maxMs = 5000,
): Promise<T> {
  for (let n = 0; ; n++) {
    try {
      return await aufruf(AbortSignal.timeout(2000));   // Timeout pro Versuch
    } catch (fehler) {
      if (n >= versuche - 1 || !istVoruebergehend(fehler)) throw fehler;
      const obergrenze = Math.min(maxMs, basisMs * 2 ** n);
      const warten = Math.random() * obergrenze;          // Full Jitter
      await new Promise((r) => setTimeout(r, warten));
    }
  }
}

// Ein Schlüssel pro Zahlung, für alle Versuche derselbe
const schluessel = crypto.randomUUID();
const zahlung = await mitRetry((signal) =>
  fetch("http://zahlung:8080/zahlungen", {
    method: "POST",
    signal,
    headers: { "Content-Type": "application/json", "Idempotency-Key": schluessel },
    body: JSON.stringify({ bestellung: "B-4711", betragRappen: 8900 }),
  }).then((antwort) => {
    if (antwort.status >= 500 || antwort.status === 429) throw new VoruebergehenderFehler(antwort.status);
    return antwort.json();
  }),
);

Idempotenz-Schlüssel: Retry ohne doppelte Abbuchung

Gefährlicher Fall: Die Zahlung ist gebucht, aber die Antwort geht unterwegs verloren. Der Client sieht nur einen Timeout und wiederholt. Ohne Schutz wird das Konzertticket zweimal belastet. Darum schickt der Client einen Idempotenz-Schlüssel mit, der für alle Versuche gleich bleibt. Der Server speichert Schlüssel und Antwort. Kommt derselbe Schlüssel nochmals, liefert er die gespeicherte Antwort, statt nochmals zu buchen. GET, PUT und DELETE sind laut HTTP schon idempotent, POST nicht.

POST /zahlungen HTTP/1.1
Host: zahlung.intern
Content-Type: application/json
Idempotency-Key: 9f1c2e7a-5b3d-4c1e-8a2f-0d6b7c9e1a42

{"bestellung": "B-4711", "betragRappen": 8900}

--- Antwort geht verloren, Client wiederholt mit demselben Schlüssel ---

HTTP/1.1 201 Created
Content-Type: application/json

{"zahlung": "Z-981", "status": "GEBUCHT"}   // gespeicherte Antwort, keine zweite Buchung
Falle: Retry ohne Idempotenz macht aus einem Netzwerkfehler einen Geldfehler. Erzeuge den Schlüssel einmal pro fachlichem Vorgang (pro Zahlung), nicht pro Versuch. Ein neuer Schlüssel bei jedem Versuch schützt gar nichts.

Circuit Breaker: der Schutzschalter

Ein Retry hilft bei kurzen Störungen. Ist der Partner aber minutenlang krank, verschlimmern Retries die Lage: Jeder Aufruf wartet bis zum Timeout und belastet den kranken Dienst zusätzlich. Der Circuit Breaker zählt Fehler. Sind es zu viele, «springt die Sicherung raus»: Er weist Aufrufe sofort ab und ruft den Fallback auf. Nach einer Wartezeit lässt er wenige Probe-Aufrufe durch. Klappen sie, schliesst er wieder.

ZustandWas passiert mit Aufrufen?Wechsel
geschlossen (closed)gehen normal durch, Fehler werden gezähltzu viele Fehler → offen
offen (open)werden sofort abgewiesen, FallbackWartezeit vorbei → halb offen
halb offen (half-open)nur wenige Probe-Aufrufe gehen durchProben ok → geschlossen, eine scheitert → offen

Ausprobieren: Schalte den Dienst auf «gestört» und sende Aufrufe. Beobachte, wann der Schalter öffnet. Lass dann 10 Sekunden verstreichen, schalte den Dienst wieder auf «gesund» und sende Probe-Aufrufe. Vereinfachung: Hier öffnet der Schalter nach 3 Fehlern in Folge. Resilience4j rechnet mit einer Fehlerquote in einem Fenster (zum Beispiel 50 % der letzten 10 Aufrufe).

    Bulkhead, Fallback, Rate Limiting

    Bulkhead (Schott)

    Ein Schiff hat wasserdichte Abteilungen. Ein Leck flutet eine Abteilung, nicht das ganze Schiff. Im Dienst bekommt jeder Partner ein eigenes Kontingent: höchstens 20 gleichzeitige Aufrufe an die Zahlung, eigene 20 an das Lager. Hängt die Zahlung, bleiben Threads für Suche und Lager frei.

    Fallback (Ersatzantwort)

    Was zeigt die Seite, wenn der Aufruf scheitert? Streaming: zuletzt gültige Empfehlungen aus dem Cache oder «Beliebt in der Schweiz». Webshop: Bestellung vormerken, Zahlung später. Ein Fallback ist eine fachliche Entscheidung, keine technische.

    Rate Limiting

    Das API-Gateway lässt pro Kunde zum Beispiel 100 Anfragen pro Minute zu (Token Bucket: jede Anfrage verbraucht ein Token, Tokens füllen sich langsam nach). Wer mehr schickt, bekommt 429 Too Many Requests. So schützt du Dienste vor Überlast und vor teuren Ausreissern.

    Health Checks

    Kubernetes fragt jeden Pod regelmässig. Readiness: Bin ich bereit für Verkehr? Nein → keine Anfragen, aber kein Neustart. Liveness: Lebe ich noch? Nein → Neustart. Der Load Balancer schickt Anfragen nur an bereite Pods.

    Alles zusammen mit Resilience4j

    In Java übernimmt die Bibliothek Resilience4j die Muster. Du schreibst Annotationen an die Methode und die Grenzwerte in die Konfiguration. Die Reihenfolge von aussen nach innen ist dabei: Retry → Circuit Breaker → Rate Limiter → Time Limiter → Bulkhead → eigentlicher Aufruf.

    @Service
public class ZahlungsClient {

  private final RestClient rest;   // mit Connect- und Read-Timeout, siehe oben

  public ZahlungsClient(RestClient zahlungRest) { this.rest = zahlungRest; }

  @CircuitBreaker(name = "zahlung", fallbackMethod = "spaeterZahlen")
  @Retry(name = "zahlung")
  @Bulkhead(name = "zahlung")
  public ZahlungsAntwort belasten(ZahlungsAuftrag auftrag) {
    return rest.post()
        .uri("/zahlungen")
        .header("Idempotency-Key", auftrag.id().toString())
        .body(auftrag)
        .retrieve()
        .body(ZahlungsAntwort.class);
  }

  // Fallback: gleiche Parameter plus Throwable. Läuft bei Fehler oder offenem Schalter.
  private ZahlungsAntwort spaeterZahlen(ZahlungsAuftrag auftrag, Throwable fehler) {
    return ZahlungsAntwort.vorgemerkt(auftrag.id());
  }
}

    Warum braucht ein Circuit Breaker trotzdem noch einen Timeout?

    Der Circuit Breaker zählt Fehler. Ein Aufruf, der nie zurückkommt, ist aber kein Fehler, solange niemand abbricht. Ohne Timeout wartet der Thread ewig, der Breaker sieht nichts und öffnet nie.

    Erst der Timeout macht aus «hängt» einen zählbaren Fehler. Resilience4j kann zusätzlich langsame Aufrufe zählen (slow-call-duration-threshold).

    Schritt 4 · Konsistenz

    CAP, Replikation und eventual consistency

    Replikation: Leader und Follower

    Damit eine Datenbank einen Serverausfall übersteht und mehr Lesezugriffe schafft, hält sie Kopien (Replikate). Beim Leader-Follower-Verfahren nimmt nur der Leader Schreibzugriffe an. Er schickt jede Änderung an die Follower. Lesen darf man auch bei den Followern. Repliziert der Leader asynchron, bestätigt er den Schreibzugriff sofort und die Follower hinken kurz hinterher (replication lag). Repliziert er synchron, wartet er auf die Follower: aktueller, aber langsamer und anfälliger.

    Das CAP-Theorem

    Das CAP-Theorem betrachtet drei Eigenschaften eines replizierten Systems: Consistency (jede Leseanfrage sieht den neuesten Schreibvorgang), Availability (jede Anfrage an einen laufenden Knoten bekommt eine Antwort) und Partition tolerance (das System funktioniert weiter, obwohl Nachrichten zwischen Knoten verloren gehen). Netzwerktrennungen kommen in jedem verteilten System vor, P ist also Pflicht. Die eigentliche Aussage lautet darum: Während einer Partition musst du zwischen C und A wählen.

    CP: Konsistenz zuerstAP: Verfügbarkeit zuerst
    Bei PartitionMinderheitsseite lehnt ab oder wartetJede Seite antwortet, eventuell veraltet
    Danachnichts aufzuräumenKonflikte zusammenführen (z. B. letzter Schreiber gewinnt)
    BeispieleKontostand bei Überweisung, letzter Sitzplatz, etcd und ZooKeeper (Konfiguration, Leader-Wahl)Warenkorb, Likes, DNS, Cassandra und DynamoDB im Standard

    PACELC erweitert CAP um den Normalfall: Bei einer Partition wähle A oder C, Else (ohne Partition) wähle Latenz oder Consistency. Auch ohne Störung kostet Konsistenz Zeit, weil der Leader auf die Kopien warten muss. Cassandra ist typisch PA/EL (schnell, eventual), eine synchron replizierte relationale Datenbank PC/EC.

    Starke und eventual consistency

    Starke Konsistenz

    Nach einem bestätigten Schreibvorgang sehen alle Leser sofort den neuen Wert, als gäbe es nur eine Kopie. Nötig für Kontostände, Lagerbestände beim letzten Stück, Medikamentendosierung in der Spital-Software. Preis: höhere Latenz, bei Partition weniger Verfügbarkeit.

    Eventual consistency

    Kopien dürfen kurz abweichen. Kommen keine neuen Schreibvorgänge, gleichen sie sich irgendwann an. Gut für Likes-Zähler, Produktbewertungen, «zuletzt angesehen», Suchindex. Preis: Die Anwendung muss mit veralteten Werten leben können.

    Tipp: Zwischen den Extremen gibt es nützliche Stufen. Read-your-writes: Wer selbst schreibt, sieht seine Änderung sofort, zum Beispiel weil seine Lesezugriffe die nächsten Sekunden beim Leader landen. Das reicht oft für «Adresse geändert, Profilseite zeigt neue Adresse».
    Falle «CA-System»: Ein verteiltes System kann Partitionen nicht abbestellen. «Wir wählen C und A» heisst in Wahrheit: Bei einer Partition verhält es sich unvorhersehbar. CA gibt es nur für eine einzelne Datenbank auf einem Server.

    Kurz üben: CP oder AP?

    Frag dich: Was ist schlimmer, eine kurze Fehlermeldung oder eine veraltete oder doppelte Angabe? Viele Systeme lassen sich je nach Einstellung so oder so betreiben; hier zählt der typische Einsatz.

    Schritt 5 · Daten über mehrere Dienste

    2PC, Saga, Outbox, CQRS

    Im Monolithen buchst du Flug, Hotel und Zahlung in einer einzigen Datenbank-Transaktion: alles oder nichts (ACID). Bei Microservices hat jeder Dienst seine eigene Datenbank (database per service). Eine gemeinsame Transaktion über drei Dienste gibt es nicht gratis.

    Two-Phase Commit (2PC) und warum man es meidet

    Beim 2PC fragt ein Koordinator zuerst alle Teilnehmer: «Könnt ihr committen?» (Phase 1, prepare). Jeder sperrt seine Daten und antwortet mit Ja oder Nein. Sagen alle Ja, schickt der Koordinator «Commit» (Phase 2), sonst «Abort».

    ProblemFolge
    Sperren über zwei NetzwerkrundenDaten bleiben gesperrt, andere Anfragen warten, Durchsatz sinkt
    Koordinator fällt nach Phase 1 ausTeilnehmer bleiben gesperrt, bis er zurück ist (blockierendes Protokoll)
    Alle müssen XA unterstützenREST-Dienste, Kafka, viele NoSQL-Datenbanken und Fremddienste können es nicht
    VerfügbarkeitEin einziger langsamer Teilnehmer blockiert alle: das Gegenteil von Resilienz

    Saga: lokale Schritte mit Kompensation

    Eine Saga zerlegt den Vorgang in eine Folge lokaler Transaktionen, je eine pro Dienst. Jede committet sofort. Scheitert ein späterer Schritt, laufen für alle erledigten Schritte Kompensationen in umgekehrter Reihenfolge: neue Transaktionen, welche die Wirkung fachlich aufheben (Storno, Gutschrift).

    (zahlung.belasten,   keine)              // letzter Schritt: danach gibt es kein Zurück
  ]
  erledigt = []
  für (aktion, kompensation) in schritte:
    sagaLog.speichern(buchung.id, aktion, "GESTARTET")
    ergebnis = aktion(buchung, idempotenzSchluessel = buchung.id + aktion.name)
    wenn ergebnis.fehlgeschlagen:
      sagaLog.speichern(buchung.id, "KOMPENSIERE")
      für k in umgekehrt(erledigt):
        wiederholeBisErfolg(k, buchung)     // Kompensation darf nicht endgültig scheitern
      sagaLog.speichern(buchung.id, "KOMPENSIERT")
      return FEHLGESCHLAGEN
    erledigt.anhaengen(kompensation)
    sagaLog.speichern(buchung.id, aktion, "ERLEDIGT")
  broker.veroeffentlichen("ReiseGebucht", buchung.id)
  return GEBUCHT
    Falle Kompensation ist kein Rollback: Zwischen Reservation und Storno war das Hotelzimmer für andere belegt, vielleicht ging schon eine Bestätigungsmail raus. Eine Saga hat kein «I» aus ACID (keine Isolation). Andere sehen Zwischenstände. Plane das ein: Status «RESERVIERT» statt «GEBUCHT», Mail erst am Ende.

    Transactional Outbox: Speichern und Veröffentlichen ohne Lücke

    Der Bestellservice soll die Bestellung speichern und das Event «Bestellung erstellt» an Kafka schicken. Das sind zwei Systeme (dual write). Stürzt der Dienst zwischen beiden ab, ist die Bestellung gespeichert, aber das Lager erfährt nie davon. Umgekehrt: Event gesendet, aber DB-Commit gescheitert. Die Outbox löst das: Das Event landet in einer Tabelle outbox in derselben lokalen Transaktion wie die Bestellung. Ein Relay liest neue Outbox-Einträge und veröffentlicht sie. Entweder es pollt die Tabelle, oder ein CDC-Werkzeug wie Debezium liest das Transaktionslog der Datenbank.

    CREATE TABLE outbox (
  id            UUID         PRIMARY KEY,
  aggregat_typ  VARCHAR(50)  NOT NULL,   -- z. B. 'Bestellung'
  aggregat_id   VARCHAR(50)  NOT NULL,   -- z. B. 'B-4711'
  ereignis_typ  VARCHAR(100) NOT NULL,   -- z. B. 'BestellungErstellt'
  nutzlast      JSONB        NOT NULL,
  erstellt_am   TIMESTAMPTZ  NOT NULL DEFAULT now(),
  gesendet_am   TIMESTAMPTZ               -- NULL = noch nicht veröffentlicht
);

BEGIN;
INSERT INTO bestellung (id, kunde_id, status, total_rappen)
  VALUES ('B-4711', 'K-17', 'NEU', 8900);
INSERT INTO outbox (id, aggregat_typ, aggregat_id, ereignis_typ, nutzlast)
  VALUES (gen_random_uuid(), 'Bestellung', 'B-4711', 'BestellungErstellt',
          '{"bestellung": "B-4711", "totalRappen": 8900}');
COMMIT;   -- beides oder nichts
    @Component
class OutboxRelay {

  private final OutboxRepository outbox;
  private final KafkaTemplate<String, String> kafka;

  OutboxRelay(OutboxRepository outbox, KafkaTemplate<String, String> kafka) {
    this.outbox = outbox;
    this.kafka = kafka;
  }

  @Scheduled(fixedDelay = 1000)       // jede Sekunde nachsehen
  @Transactional
  public void veroeffentlichen() {
    for (OutboxEintrag e : outbox.findTop100ByGesendetAmIsNullOrderByErstelltAm()) {
      // Key = Aggregat-ID: alle Events einer Bestellung landen in derselben Partition, in Reihenfolge
      kafka.send("bestellungen", e.getAggregatId(), e.getNutzlast()).join();
      e.setGesendetAm(Instant.now());
    }
  }
}
    Falle «genau einmal»: Stürzt das Relay nach dem Senden, aber vor dem Commit von gesendet_am ab, sendet es das Event nach dem Neustart nochmals. Die Outbox garantiert mindestens einmal (at-least-once). Konsumenten müssen darum idempotent sein, zum Beispiel indem sie verarbeitete Event-IDs in einer Tabelle (Inbox) merken.

    CQRS und Event Sourcing (kurz)

    CQRS

    Command Query Responsibility Segregation: Schreiben und Lesen bekommen getrennte Modelle. Das Schreibmodell prüft Regeln und speichert normalisiert. Ein Projektor baut aus Events ein Lesemodell, das genau so aussieht, wie die Seite es braucht, zum Beispiel «Meine Bestellungen» mit Titel, Bild und Status in einer Zeile. Das Lesemodell ist eventual consistent: Es hinkt ein paar Millisekunden hinterher.

    Event Sourcing

    Statt den aktuellen Zustand zu speichern, speicherst du alle Ereignisse. Der Zustand ist das Ergebnis, wenn du sie der Reihe nach abspielst, wie ein Kontoauszug: Saldo = Summe aller Buchungen. Vorteil: lückenlose Historie, Lesemodelle jederzeit neu aufbaubar. Nachteil: Abfragen brauchen Projektionen, Schemaänderungen an alten Events sind mühsam.

    [
  {"nr": 1, "typ": "KontoEroeffnet", "konto": "CH-001"},
  {"nr": 2, "typ": "Eingezahlt",     "konto": "CH-001", "betragRappen": 10000},
  {"nr": 3, "typ": "Abgehoben",      "konto": "CH-001", "betragRappen": 3000}
]
// Abspielen: 0 + 10000 - 3000 = 7000 Rappen, also 70.00 CHF Saldo
    Braucht jede Microservice-Architektur CQRS und Event Sourcing?

    Nein. Beide Muster machen ein System komplexer: zusätzliche Projektoren, eventual consistency im Lesepfad, Versionierung von Events.

    CQRS lohnt sich, wenn Lesen und Schreiben sehr verschieden sind (viele Leser, komplexe Ansichten). Event Sourcing lohnt sich, wenn die Historie selbst fachlich wichtig ist (Buchhaltung, Audit, Versicherungsfälle). Für einen einfachen CRUD-Dienst reicht eine normale Tabelle.

    Schritt 6 · Beobachtbarkeit

    Sehen, wo es klemmt

    Resilienzmuster verstecken Fehler: Der Fallback antwortet freundlich, obwohl die Zahlung seit einer Stunde kaputt ist. Darum braucht jedes verteilte System Beobachtbarkeit (observability) mit drei Säulen.

    Logs = Tagebuch

    Einzelne Ereignisse mit Zeit, Dienst und Text, am besten als JSON. Zentral gesammelt (Loki, Elasticsearch).

    Metriken = Tacho

    Zahlen über die Zeit: Anfragen pro Sekunde, Fehlerquote, Antwortzeit, Zustand des Circuit Breakers (Prometheus, Grafana).

    Traces = Reiseroute

    Der Weg einer Anfrage durch alle Dienste, mit Dauer je Station (OpenTelemetry, Jaeger).

    Correlation-ID = Fallnummer

    Eine Kennung, die jede Anfrage im Header mitnimmt. Damit findest du alle Logzeilen eines Klicks in allen Diensten.

    Schritt 8 · Vom Text zur Architektur

    Modellierungsübungen

    Lies jeweils den Text und unterstreiche im Kopf zuerst die Nomen (Bausteine), dann die Verben (Verbindungen). «ruft auf», «fragt» = synchron. «veröffentlicht», «abonniert» = asynchron. «speichert», «liest» = Datenzugriff. Die Aufgaben werden schwieriger. Die letzte entspricht dem Lösungsfilm.

    Bedienung: Baustein in der Liste antippen legt ihn auf die Fläche. Verbindungsart wählen, dann Start- und Zielbaustein antippen. «Prüfen» zeigt, was stimmt.

    Selbsttest

    Sitzt es?

    Das Wichtigste auf einen Blick

    • Teilausfälle sind normal. Jeder Aufruf übers Netz braucht einen Timeout. Innere Timeouts samt Retries sind kürzer als äussere.
    • Retry nur mit Backoff, Jitter und Idempotenz-Schlüssel, nur bei vorübergehenden Fehlern und nur an einer Stelle.
    • Circuit Breaker: geschlossen → (zu viele Fehler) offen → (Wartezeit) halb offen → (Proben ok) geschlossen. Offen heisst: sofort Fallback, kein Aufruf. Bulkhead grenzt Ressourcen je Partner ab.
    • CAP: Bei einer Partition entweder Konsistenz (ablehnen) oder Verfügbarkeit (eventuell veraltet antworten). PACELC: ohne Partition Latenz gegen Konsistenz.
    • Saga statt 2PC: lokale Transaktionen, bei Fehler Kompensationen rückwärts. Choreografie über Events, Orchestrierung über einen Koordinator mit Saga-Log.
    • Outbox: Event in derselben lokalen Transaktion speichern, Relay veröffentlicht mindestens einmal, Konsumenten sind idempotent. Beobachtbarkeit mit Logs, Metriken, Traces und Correlation-ID.
