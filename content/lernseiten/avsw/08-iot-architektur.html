IoT-Referenzarchitektur: vom Sensor zur Entscheidung

Ein Kühlschrank meldet seine Temperatur, eine Maschine sagt ihren Ausfall voraus, eine Strassenlampe dimmt sich selbst. Dahinter steckt immer dieselbe Architektur: Geräte am Rand, eine Plattform in der Mitte, Fachanwendungen am Ende, dazwischen drei Netze. Schritt 0 · Ohne Vorwissen

Sechs Bausteine mit Alltagsbildern

Stell dir ein grosses Spital vor. Überall gibt es Menschen, die etwas wahrnehmen, andere, die handeln, und eine Zentrale, die alles zusammenführt. Genau so ist eine IoT-Lösung gebaut.

Sensor = Fieberthermometer

Misst etwas in der echten Welt (Temperatur, Feuchte, Position) und macht daraus eine Zahl. Er handelt nicht selbst.

Aktor = Pflegerin, die das Fenster öffnet

Setzt einen Befehl in eine Wirkung um: Ventil auf, Motor an, Schloss zu, Licht dimmen.

Edge Gateway = Stationszimmer

Sammelt die Meldungen der ganzen Abteilung, fasst sie zusammen und reagiert sofort, wenn es eilt, auch wenn die Zentrale nicht erreichbar ist.

Plattform = Leitstelle

Nimmt alle Meldungen an, prüft sie, legt sie ab, wertet sie aus, zeigt sie auf grossen Bildschirmen und schickt Anweisungen zurück.

Netze = Rohrpost, Telefon, Kurier

Im Haus die Rohrpost (Field Network), zur Leitstelle das Telefon (Access Network), zur Verwaltung der Kurier (Service Network).

Fachanwendung = Verwaltung

Die Verwaltung (ERP, CRM) braucht nicht jeden Fieberwert, sondern Ergebnisse: «Gerät 7 muss gewartet werden.»

Kurz üben: Sensor oder Aktor?

Frag dich: Misst das Teil etwas, oder verändert es etwas in der Welt?

Schritt 2 · IoT-Device, Wearables

Was ein Ding «smart» macht

Ein IoT-Device ist ein cyberphysisches Ding: Es lebt in einem physischen Kontext (Wohnung, Strasse, Werkhalle) und hat eine digitale Seite. Sensoren nehmen die Umgebung wahr, Aktoren verändern sie. Dazwischen sitzt ein Embedded System mit einem Chip (MPU), das die Werte verarbeitet und mit der IoT-Plattform spricht. Viele solche Dinge zusammen ergeben Ambient Intelligence: eine Umgebung, die mitdenkt, ohne dass du sie bedienen musst.

Vier smarte Dinge auseinandergenommen

Wähle ein Ding. Das Bild zeigt, was es misst, was es bewirkt, was der Chip tut und was zur Plattform fliesst.

Wearables und Datenbrillen

Ein Wearable trägst du am Körper: Smartwatch, Fitnessband, Datenbrille, Sensor im Arbeitshandschuh. Es ist ein mobiles IoT-Device mit Display, Lautsprecher oder Vibration. Jedes Wearable erfüllt drei Aufgaben, und jede hat ihre Grenze:

1 · Wahrnehmen

Sensoren sammeln Daten: Puls, Bewegung, Position, Kamerabild, Sprache.

Grenze: Jeder Sensor kostet Strom. Der Akku ist klein.

2 · Austauschen

Das Gerät tauscht Daten aus, oft über das Handy (Bluetooth) oder das WLAN des Betriebs.

Grenze: Die Reichweite ist kurz, das Netz nicht überall stabil.

3 · Informieren

Es informiert die Trägerin über Display, Ton oder Vibration, ohne dass sie die Hände braucht.

Grenze: Es muss leicht und bequem sein, sonst trägt es niemand.

Beispiel: Datenbrille im Lager von «Gipfelsport Versand» (fiktiv)

Rina rüstet Bestellungen. Ihre Datenbrille blendet den nächsten Lagerplatz ins Sichtfeld ein und zeigt den Weg dorthin. Am Regal erfasst die Kamera der Brille den Strichcode des Artikels, sie muss nichts in die Hand nehmen. Die Brille ermittelt die Menge: Rina sagt «drei», ein Bilderkennungsmodell zählt zur Kontrolle mit. Dann zeigt die Brille die nächste Anweisung: «Fach B-14, zwei Stück». Die Rüstaufträge kommen aus dem ERP (Control Flow), die Bestätigungen gehen zurück (Data Flow).

Schritt 3 · Die Referenzarchitektur

IoT-Referenzarchitektur als interaktive Landkarte

Die Referenzarchitektur hat drei Tiers von links nach rechts: Edge Tier (Geräte und Edge Gateway), Platform Tier (die IoT-Plattform) und Enterprise Tier (Fachanwendungen). Unter dem Edge Tier liegt der Data Provider für fremde Daten. Zwischen den Tiers liegen drei Netze: Field Network im Edge Tier, Access Network zwischen Edge und Plattform, Service Network zwischen Plattform und Fachanwendungen. Daten fliessen nach rechts (Data Flow), Befehle zurück nach links (Control Flow).

Landkarte: Was willst du sehen?

Wähle einen Teil. Er wird im Diagramm hervorgehoben, der Rest tritt zurück.

Tippe jede Komponente und jedes Paket an: Der Steckbrief ist eine prüfungstaugliche Beschreibung (was, kann, wofür, Technologie, warum). Spiel die drei Abläufe ab und schalte den Ausfall-Modus ein, z. B. für das Access Network oder das DBMS. Das Diagramm ist breit: Ziehen verschiebt, ⛶ passt die ganze Referenz ein.

Edge Tier

Nahe an der physischen Welt. Viele Geräte (Multiplizität *) hängen über ein sparsames Feldnetz an einem Edge Gateway.

Warum ein Gateway? Ein Sensor mit Knopfbatterie kann kein TLS über Mobilfunk sprechen. Das Gateway kann.

Platform Tier

Eingang, Aufbereitung, Speicherung, Auswertung, Anzeige und Steuerung an einer Stelle, für tausende Geräte gleich.

Warum zentral? Geräteverwaltung, Sicherheit und Datenmodell sind sonst je Projekt neu zu bauen.

Enterprise Tier

CRM, PLM, ERP nutzen Ergebnisse, keine Rohdaten: Serviceauftrag, Abrechnung nach Verbrauch, Produktverbesserung.

Warum getrennt? Fachanwendungen sollen nicht wissen müssen, welches Funkprotokoll ein Sensor spricht.

Data Provider

Liefert fremde Daten (Wetter, Strompreise, Verkehr) über das Access Network in die Plattform, wie ein Gerät.

Warum? Viele Auswertungen werden erst mit Kontext aussagekräftig.

Data Flow, Control Flow und Ausfall

Data Flow (nach rechts)

Sensor → Field Network → Edge Gateway → Access Network → Platform Gateway → Data Transform → DBMS → Analytics → Dashboard und über das Service Network → Domain Application.

Control Flow (nach links)

Domain Application oder Mensch am UI → Operations Algorithms & UI → Access Network → Edge Gateway → Field Network → Aktor im Gerät. Operations liest dazu Zustände aus dem DBMS.

Ausfall des Access Network

Die Geräte messen weiter. Das Edge Gateway puffert die Werte und reagiert lokal auf Grenzwerte. Nach der Störung sendet es nach, die Plattform füllt die Lücke.

Merke: Die Fachanwendung schaltet nie direkt einen Aktor. Jeder Befehl läuft über Operations in der Plattform. Nur dort kennt man Gerätezustand, Berechtigung und Protokoll.

Bereits modelliert: Velo-Flotte «Alpenrad» (fiktiv)

So sieht die Referenz für einen konkreten Fall aus: E-Bikes und Ladestationen in einer Stadt, Plattform bei AWS, Abo-Verwaltung im CRM und Wartung im ERP. Jede Komponente trägt die konkrete Technologie, jede Verbindung ist beschriftet. Drei Abläufe: Velo entsperren (Control Flow), Akku-Prognose (Data Flow), Funkloch an der Station.

    Schritt 5 · MQTT, CoAP, AMQP, OPC UA

    Protokolle zwischen Gerät und Plattform

    IoT-Geräte haben wenig Strom, wenig Speicher und oft ein wackliges Netz. HTTP mit grossen Kopfzeilen und ständigem Nachfragen («gibt es Neues?») passt schlecht. Darum gibt es Protokolle, die genau dafür gebaut sind. Der Klassiker ist MQTT.

    MQTT: Publish/Subscribe über einen Broker

    Broker und Topics

    Geräte publizieren Nachrichten unter einem Topic (z. B. bergblick/keller-2/klima/fuehler-07) an den Broker. Wer ein Topic abonniert, bekommt die Nachrichten. Sender und Empfänger kennen sich nicht.

    Wildcards

    + ersetzt genau eine Ebene, # alle restlichen Ebenen (nur am Ende). bergblick/+/klima/+ liefert alle Klimafühler aller Keller.

    QoS 0, 1, 2

    0 höchstens einmal (kann verloren gehen), 1 mindestens einmal (Duplikate möglich), 2 genau einmal (vierfacher Handschlag, langsamer).

    Retained und Last Will

    Retained: Der Broker merkt sich die letzte Nachricht eines Topics und gibt sie neuen Abonnenten sofort. Last Will: Bricht ein Gerät unerwartet ab, publiziert der Broker die vorher hinterlegte Nachricht «offline».

    Warum MQTT? Der feste Kopf ist nur 2 Byte gross, die Verbindung bleibt offen (der Broker kann Befehle sofort zum Gerät schieben), und der Broker entkoppelt Tausende Geräte von den Auswertungen. MQTT läuft über TCP, gesichert mit TLS (Port 8883). In der Referenz steckt der Broker im Platform Gateway, oft auch ein kleiner im Edge Gateway.

      Schritt 6 · MQTT im Code

      Topic-Struktur, JSON-Telemetrie, Publish und Subscribe

      Drei Programme der Käserei Bergblick zeigen, wo im Diagramm welcher Code läuft. Das Edge Gateway publiziert, Data Transform abonniert, Operations schickt einen Befehl zurück.

      Topic-Struktur festlegen

      Ein Topic ist eine Adresse von grob nach fein. Lege die Ebenen einmal fest, dann funktionieren Wildcards. Regeln: Kleinbuchstaben, kein Schrägstrich am Anfang, keine Leerzeichen, Befehle und Status auf eigenen Topics.

      # firma / standort-oder-fahrzeug / bereich / gerät [/ art]
bergblick/keller-2/klima/fuehler-07              # Telemetrie (Data Flow)
bergblick/keller-2/klappe/klappe-1/befehl        # Befehl (Control Flow)
bergblick/keller-2/klappe/klappe-1/status        # Bestätigung des Aktors
bergblick/edge-1/status                          # Last Will: "offline", retained

      JSON-Telemetrie

      {
  "geraet": "fuehler-07",
  "zeit": "2026-11-02T06:41:00Z",
  "temperatur_c": 13.2,
  "feuchte_pct": 82,
  "anzahl_werte": 6,
  "batterie_pct": 71
}

      Eine Nachricht je Gerät und Minute: anzahl_werte zeigt, dass das Edge Gateway 6 Messungen gemittelt hat. Die Zeit steht in UTC, damit Geräte in allen Zeitzonen vergleichbar sind.

      läuft in: Edge Gateway (Edge Tier)

      Publish mit Python und paho-mqtt

      Das Gateway sendet jede Minute den Mittelwert mit QoS 1, hinterlegt einen Last Will und hört auf Befehle für die Lüftungsklappe.

      import json, time
import paho.mqtt.client as mqtt

BROKER = "iot.bergblick.example"          # Platform Gateway
client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id="edge-1")
client.tls_set(ca_certs="ca.pem", certfile="edge-1.crt", keyfile="edge-1.key")
client.will_set("bergblick/edge-1/status", "offline", qos=1, retain=True)

def bei_befehl(client, userdata, msg):              # Control Flow kommt an
    befehl = json.loads(msg.payload)
    klappe_stellen(befehl["oeffnung_pct"])           # Aktor über Field Network

client.on_message = bei_befehl
client.connect(BROKER, 8883)
client.subscribe("bergblick/keller-2/klappe/+/befehl", qos=1)
client.publish("bergblick/edge-1/status", "online", qos=1, retain=True)
client.loop_start()

while True:
    werte = feldnetz_lesen("fuehler-07", sekunden=60)  # 6 Werte aus LoRaWAN
    nachricht = {"geraet": "fuehler-07", "zeit": jetzt_utc(), "feuchte_pct": mittel(werte), "anzahl_werte": len(werte)}
    client.publish("bergblick/keller-2/klima/fuehler-07", json.dumps(nachricht), qos=1)
    time.sleep(60)

      Bricht das Access Network ab, hält paho die QoS-1-Nachrichten im Speicher und sendet sie nach dem Wiederverbinden. Für längere Ausfälle schreibt ein echtes Gateway zusätzlich in eine lokale Datei oder Datenbank.

      läuft in: Data Transform (Platform Tier)

      Subscribe mit JavaScript und mqtt.js

      Data Transform abonniert alle Klimafühler, prüft die Werte, ergänzt Keller und Charge und schreibt in die Zeitreihen-Datenbank.

      import mqtt from "mqtt";

const client = mqtt.connect("mqtts://iot.bergblick.example:8883", {
  clientId: "data-transform-1", clean: false,   // Sitzung behalten: nichts verpassen
});

client.on("connect", () => {
  client.subscribe("bergblick/+/klima/+", { qos: 1 });
});

client.on("message", async (topic, payload) => {
  const [, keller, , fuehler] = topic.split("/");
  const wert = JSON.parse(payload.toString());
  if (wert.feuchte_pct < 0 || wert.feuchte_pct > 100) return;   // unplausibel: verwerfen
  await zeitreihe.schreiben({                                 // DBMS
    zeit: wert.zeit, keller, fuehler,
    feuchte: wert.feuchte_pct, charge: await chargeIm(keller),
  });
});

      Weil QoS 1 Duplikate erlaubt, schreibt Data Transform idempotent: Ein Wert mit gleichem Gerät und gleicher Zeit überschreibt sich selbst statt doppelt zu zählen.

      läuft in: Operations Algorithms & UI (Platform Tier)

      Befehl zurück an den Aktor (Control Flow)

      function klappeStellen(keller, klappe, oeffnungPct) {
  const befehl = { oeffnung_pct: oeffnungPct, grund: "Feuchte unter Sollwert" };
  client.publish(`bergblick/${keller}/klappe/${klappe}/befehl`, JSON.stringify(befehl), { qos: 1 });
}

      Befehle bekommen kein «retained». Sonst würde ein Gerät nach jedem Neustart einen alten Befehl nochmals ausführen.

      Schritt 8 · Wo wird gerechnet?

      Edge Computing oder Cloud Computing

      Edge Computing rechnet nahe beim Gerät, im Edge Gateway oder sogar im Gerät. Cloud Computing rechnet zentral im Platform Tier. Beides gehört zusammen: Am Rand wird schnell und lokal reagiert, in der Cloud wird über alle Standorte gelernt und gesteuert.

      KriteriumEdge (Edge Gateway, Gerät)Cloud (Platform Tier)
      ReaktionszeitMillisekunden, ohne Weg durchs InternetZehntel bis ganze Sekunden, abhängig vom Netz
      BandbreiteVerdichtet vor Ort, sendet nur Mittelwerte oder EreignisseBraucht alle Daten, die ausgewertet werden sollen
      NetzausfallArbeitet weiter, puffertSieht nichts, bis die Verbindung zurück ist
      RechenleistungBegrenzt durch die Hardware vor OrtPraktisch beliebig skalierbar, auch für ML-Training
      DatenschutzRohdaten (z. B. Kamerabilder) bleiben vor OrtDaten verlassen den Standort
      BetriebViele verteilte Geräte zu warten und zu aktualisierenZentral, ein Ort für Updates

      Schritt 9 · Industrie 4.0

      RAMI 4.0: drei Dimensionen als Würfel

      Das Referenzarchitekturmodell Industrie 4.0 (RAMI 4.0) ordnet jedes Thema einer vernetzten Fabrik in einen Würfel mit drei Achsen ein. So reden Maschinenbauer, Software-Firmen und Betreiber über dasselbe Kästchen. Senkrecht stehen die Layers (vom physischen Ding bis zum Geschäftsprozess), waagrecht der Life Cycle & Value Stream (vom Typ in der Entwicklung bis zum einzelnen Exemplar im Betrieb), in die Tiefe die Hierarchy Levels (vom Produkt bis zur vernetzten Welt).

      Würfel erkunden: Spritzgiessmaschine im Kunststoffwerk Thur (fiktiv)

      Brücke zur IoT-Referenz: Die Layers passen gut auf die Tiers. Asset und Integration entsprechen den Geräten mit Sensoren und Aktoren im Edge Tier, Communication den Netzen und Protokollen (OPC UA, MQTT), Information dem Data Transform und dem DBMS, Functional der Analytics und Operations, Business den Domain Applications im Enterprise Tier.
      Verwaltungsschale: In Industrie 4.0 bekommt jedes Asset eine digitale «Verwaltungsschale» (Asset Administration Shell). Asset plus Verwaltungsschale ergeben eine Industrie-4.0-Komponente. Das ist der Gedanke des Digital Twin in genormter Form.
      Schritt 10 · Vorgehen und Fallen

      Eine IoT-Lösung als UML-Komponentendiagramm modellieren

      So gehst du vor

      1. Geräte sammeln: Welche Dinge messen (Sensoren), welche wirken (Aktoren)? Teile sie in stationäre und mobile IoT Devices. Die Multiplizität * zeigt: viele.
      2. Edge Tier bauen: Field Network mit der Technologie im Namen (z. B. «Field Network (LoRaWAN)»), dahinter das Edge Gateway mit seinen Aufgaben.
      3. Data Provider prüfen: Nennt der Auftrag fremde Daten (Wetter, Preise)? Dann Paket «Data Provider» mit dem externen Dienst.
      4. Access Network: zwischen Edge und Plattform, Verbindung mit Protokoll beschriften (meist MQTT).
      5. Platform Tier: Platform Gateway → Data Transform → DBMS → Analytics → Dashboard, dazu Operations Algorithms & UI. Nur, was der Auftrag braucht.
      6. Service Network und Enterprise Tier: konkrete Domain Applications (ERP, CRM, PLM) mit ihrem Zweck.
      7. Flüsse und Beschreibungen: Data Flow und Control Flow erkennbar beschriften, je Komponente 2–3 Sätze: was, wofür, warum.
      Falle 1 · Zwei Gateways verwechseln: Das Edge Gateway steht vor Ort und spricht das Feldnetz. Das Platform Gateway ist der Eingang der Plattform in der Cloud. Wer nur ein «Gateway» zeichnet, verliert den Ort, an dem bei Netzausfall gepuffert wird.
      Falle 2 · Control Flow vergessen oder abkürzen: Ohne Rückweg kann die Lösung nur zuschauen. Und: Das ERP schaltet nicht direkt den Aktor. Der Befehl läuft über Operations Algorithms & UI, das Access Network und das Edge Gateway.
      Falle 3 · Infrastruktur als Komponente: Web-Server, ein zusätzlicher Unternehmens-Broker oder eine Integration Middleware gehören nicht in die IoT-Referenz. Der MQTT-Broker steckt im Platform Gateway.
      Falle 4 · Dashboard am Gerät: Das Dashboard holt seine Daten aus der Plattform (Analytics, DBMS), nie direkt vom Sensor. Rohdaten gehen zuerst durch Data Transform.

      Σ Merksätze

      Auf einen Blick

      • Ein IoT-Device ist ein cyberphysisches Ding: Sensoren messen, Aktoren wirken, ein Embedded System mit MPU verbindet beides mit der IoT-Plattform.
      • Drei Tiers: Edge (Geräte, Field Network, Edge Gateway), Platform (Platform Gateway, Data Transform, DBMS, Analytics, Dashboard, Operations), Enterprise (Domain Applications). Dazu der Data Provider.
      • Drei Netze: Field Network im Edge Tier, Access Network zur Plattform, Service Network zu den Fachanwendungen.
      • Data Flow läuft vom Sensor bis zum ERP, Control Flow über Operations zurück zum Aktor. Fällt das Access Network aus, puffert das Edge Gateway und reagiert lokal.
      • MQTT: Publish/Subscribe über einen Broker, Topics mit + und #, QoS 0/1/2, Retained und Last Will. CoAP für winzige Geräte, AMQP zum Unternehmens-Broker, OPC UA für Maschinen.
      • Im Diagramm: Tiers als Pakete, Netze als Komponenten zwischen den Tiers, konkrete Technologie im Namen, jede Verbindung beschriftet, keine Web-Server und kein Zusatz-Broker. RAMI 4.0 ordnet Industrie-Themen nach Layers, Life Cycle und Hierarchy Levels.
