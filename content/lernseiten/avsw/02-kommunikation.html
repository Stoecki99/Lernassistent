Schritt 0 · Ohne Vorwissen

Fünf Begriffe, die du zuerst brauchst

Ein verteiltes System besteht aus mehreren Programmen, die auf verschiedenen Rechnern laufen. Man nennt sie Dienste (englisch services). Ein Dienst kann einem anderen nicht einfach eine Variable zeigen. Er muss ihm über das Netzwerk etwas schicken. Wie er das tut, entscheidet, wie stark die Dienste voneinander abhängen.

Synchron = Telefonanruffragen → warten → Antwort

Du rufst an und bleibst am Apparat, bis du die Antwort hast. Beispiel: Die Shop-App fragt den Zahlungsdienst «Ist die Karte gedeckt?» und wartet.

Asynchron = Briefkasteneinwerfen → weiterarbeiten

Du wirfst einen Brief ein und gehst. Der Empfänger liest ihn, wenn er Zeit hat. Beispiel: Der Bestellservice legt «Etikett drucken» in eine Warteschlange.

Event = Durchsage«BestellungAufgegeben»

Eine Meldung, dass etwas passiert ist, wie eine Durchsage im Bahnhof. Wer sich dafür interessiert, hört zu. Der Absender weiss nicht, wer zuhört.

Message Broker = PostRabbitMQ, Kafka

Ein eigenes Programm zwischen Sender und Empfänger. Es nimmt Nachrichten an, bewahrt sie auf und stellt sie zu, auch wenn der Empfänger gerade nicht läuft.

API = SpeisekarteGET /restaurants

Die Schnittstelle (Application Programming Interface) sagt, was ein Dienst anbietet und wie man es bestellt. Was in der Küche passiert, sieht der Gast nicht.

Nachrichten gibt es in drei Sorten. Ein Befehl (command) verlangt etwas: «Storniere Bestellung 42». Ein Event meldet etwas Vergangenes: «Bestellung 42 wurde storniert». Eine Abfrage (query) will nur lesen: «Wie ist der Status von Bestellung 42?». Events benennt man darum in der Vergangenheit.

Kurz üben: Befehl, Event oder Abfrage?

Achte auf die Zeitform. Befehl = Imperativ (tu etwas). Event = Vergangenheit (ist passiert). Abfrage = Frage, ändert nichts.

Schritt 3 · Das Verfahren

Die Verbindungsart aus dem Text lesen

In der Prüfung bekommst du einen Anforderungstext und zeichnest die Architektur. Die Substantive liefern die Bausteine. Die Verben liefern die Verbindungen. Stell dir zu jedem Verb zwei Fragen: Braucht der Absender die Antwort, um weiterzumachen? Dann synchron. Darf der Empfänger gerade weg sein? Dann asynchron.

ArtSignalwörter im TextPfeil
synchronfragt, ruft auf, prüft sofort, wartet auf, braucht die Antwort, leitet weiter, erst nach der AntwortAufrufer → Aufgerufener
asynchronveröffentlicht, sendet ein Event, abonniert, reagiert auf, stellt in die Queue, holt aus der Queue, im Hintergrund, später, ohne zu wartenSender → Broker → Empfänger
Datenspeichert, liest, schreibt, legt ab, eigene Datenbank, hält im CacheDienst → Speicher

Das Verfahren für jede Modellierungsaufgabe:

  1. Lesen und alle Systeme, Dienste und Speicher markieren.
  2. Bausteine legen, aber nur, was im Text steht. Alles andere ist ein Ablenker.
  3. Verben lesen und je eine Verbindung ziehen: Wer ruft oder sendet? Das ist der Start des Pfeils.
  4. Art festlegen mit der Signalwort-Tabelle.
  5. Prüfen: Hat jede Verbindung ein Signalwort? Greift jeder Dienst nur auf seine eigene Datenbank zu?
Falle 1: «schickt» ist nicht automatisch asynchron. «Die App schickt die Anfrage und zeigt das Ergebnis an» heisst: Sie wartet. Entscheidend ist, ob jemand auf die Antwort wartet, nicht das Verb «schicken».
Falle 2: Liegt ein Broker dazwischen, sind beide Pfeile asynchron: Sender → Broker und Broker → Empfänger. Ein synchroner Pfeil vom Sender direkt zum Empfänger wäre eine zweite, zusätzliche Kopplung.
Falle 3: Ein Dienst liest nie direkt die Datenbank eines anderen Dienstes. Braucht er dessen Daten, fragt er den Dienst (synchron) oder hält eine eigene Kopie aus Events (asynchron). Das Prinzip heisst database per service.
Synchron oder asynchron? «Das Gateway leitet die Anfrage an den Bestellservice weiter und gibt dessen Antwort an die App zurück.»

Synchron. Das Gateway wartet auf die Antwort des Bestellservice, denn es muss sie zurückgeben. Ein Gateway ist fast immer ein synchroner Zwischenhalt: Es leitet HTTP-Anfragen weiter.

Und hier? «Der Bestellservice antwortet sofort mit 202 Accepted. Die Rechnung erstellt der Rechnungsservice im Hintergrund.»

Die Antwort an den Client ist synchron, aber kurz: «Ich habe es angenommen». Die Verbindung Bestellservice → Rechnungsservice ist asynchron: «im Hintergrund» ist das Signalwort. Technisch läuft sie über eine Queue oder ein Topic. Statuscode 202 heisst genau das: angenommen, aber noch nicht erledigt.

Schritt 4 · REST und OpenAPI

REST: Ressourcen, Verben, Statuscodes

REST (Representational State Transfer) ist kein Protokoll, sondern ein Stil für Schnittstellen über HTTP. Die Idee: Es gibt Ressourcen mit eigenen Adressen, zum Beispiel /bestellungen/B-4711. Was du damit tust, sagt das HTTP-Verb. Wie es ausgegangen ist, sagt der Statuscode. Die Daten reisen meist als JSON.

Ressourcen statt Aktionen

Die Adresse ist ein Nomen in der Mehrzahl. Die Aktion steckt im Verb.

  • ✓ POST /bestellungen
  • ✓ GET /restaurants/7/gerichte
  • ✓ DELETE /bestellungen/B-4711
  • ✗ POST /erstelleBestellung
  • ✗ GET /loescheBestellung?id=4711

Zustandslos (stateless)

Jede Anfrage bringt alles mit, was der Server braucht, zum Beispiel das Token im Header Authorization. Der Server merkt sich zwischen zwei Anfragen nichts über den Client. Darum kann jede Anfrage auf einer anderen Instanz landen. So lässt sich ein Dienst einfach skalieren.

Kommt keine Antwort, weisst du nicht, ob die Anfrage angekommen ist. Eine idempotente Anfrage darfst du gefahrlos wiederholen (retry).

Dieselbe Schnittstelle in Java mit Spring

@RestController
@RequestMapping("/api/bestellungen")
public class BestellController {

  private final BestellService service;

  public BestellController(BestellService service) {
    this.service = service;
  }

  // GET /api/bestellungen/B-4711 → 200 oder 404
  @GetMapping("/{id}")
  public ResponseEntity<BestellungDto> lesen(@PathVariable String id) {
    return service.finden(id)
        .map(ResponseEntity::ok)
        .orElse(ResponseEntity.notFound().build());
  }

  // POST /api/bestellungen → 201 Created mit Location-Header
  @PostMapping
  public ResponseEntity<BestellungDto> anlegen(
      @Valid @RequestBody NeueBestellung neu,
      @RequestHeader("Idempotency-Key") String schluessel) {
    BestellungDto b = service.anlegen(neu, schluessel); // gleicher Schlüssel → gleiche Bestellung
    URI ort = URI.create("/api/bestellungen/" + b.id());
    return ResponseEntity.created(ort).body(b);
  }
}

OpenAPI: der Vertrag zur Schnittstelle

Eine OpenAPI-Datei beschreibt alle Adressen, Parameter, Antworten und Datentypen. Andere Teams lesen sie wie eine Bedienungsanleitung. Werkzeuge erzeugen daraus eine klickbare Doku (Swagger UI), Client-Code und Tests. Arbeitet ein Team zuerst am Vertrag und erst dann am Code, heisst das API first.

Falle: POST ist nicht idempotent. Wiederholt die App nach einem Timeout einfach dieselbe POST-Anfrage, entstehen zwei Bestellungen und zwei Belastungen. Abhilfe: ein Idempotency-Key, den der Server speichert, oder eine vom Client erzeugte ID mit PUT /bestellungen/{id}.
Falle: 401 heisst «Wer bist du?» (nicht angemeldet). 403 heisst «Ich weiss, wer du bist, aber du darfst das nicht.» Der Name «Unauthorized» bei 401 ist historisch missglückt.
Ist DELETE wirklich idempotent? Der zweite Aufruf liefert doch 404 statt 204.

Ja. Idempotenz betrifft den Zustand auf dem Server, nicht den Statuscode. Nach dem ersten und nach dem zweiten DELETE ist die Bestellung weg. Der Zustand ist derselbe. Dass die Antwort beim zweiten Mal 404 lautet, ändert daran nichts.

Warum ist PATCH nicht automatisch idempotent?

Es kommt darauf an, was im Body steht. {"status": "STORNIERT"} setzt einen Wert. Zweimal gesetzt ist dasselbe, also idempotent. Eine Anweisung wie {"op": "erhoehe", "feld": "anzahl", "um": 1} erhöht bei jedem Aufruf. Nach zwei Aufrufen ist die Anzahl um 2 höher, also nicht idempotent.

Schritt 5 · gRPC und GraphQL

Zwei Alternativen zu REST

gRPC ist ein Framework für Fernaufrufe (Remote Procedure Call), ursprünglich von Google. Du rufst eine Methode eines anderen Dienstes auf, fast als wäre sie lokal. Drei Dinge machen gRPC aus:

  • Protocol Buffers (Protobuf): Der Vertrag steht in einer .proto-Datei. Ein Generator erzeugt daraus Client- und Server-Code für Java, Go, Python, C# und viele weitere Sprachen.
  • Binär statt Text: Nachrichten sind kompakt und schnell zu verarbeiten. Dafür kannst du sie nicht mehr von Auge lesen wie JSON.
  • HTTP/2: Viele Aufrufe teilen sich eine Verbindung, und es gibt Streaming in beide Richtungen.
syntax = "proto3";
package lieferung.v1;
option java_package = "ch.beispiel.lieferung.v1";
option java_multiple_files = true;

service Tracking {
  // Unary: eine Anfrage, eine Antwort
  rpc HoleStatus (StatusAnfrage) returns (StatusAntwort);
  // Server-Streaming: laufend neue Positionen der Kurierin
  rpc VerfolgeKurier (StatusAnfrage) returns (stream Position);
}

message StatusAnfrage { string bestell_id = 1; }

message StatusAntwort {
  string bestell_id  = 1;
  Status status      = 2;
  int32  eta_minuten = 3;   // Feldnummern nie wiederverwenden
}

enum Status { UNBEKANNT = 0; IN_KUECHE = 1; UNTERWEGS = 2; GELIEFERT = 3; }

message Position { double breite = 1; double laenge = 2; int64 zeit_ms = 3; }
ManagedChannel kanal = ManagedChannelBuilder
    .forAddress("tracking", 9090)
    .usePlaintext()                       // nur intern, sonst TLS
    .build();
TrackingGrpc.TrackingBlockingStub stub = TrackingGrpc.newBlockingStub(kanal);

StatusAnfrage anfrage = StatusAnfrage.newBuilder().setBestellId("B-4711").build();

// Unary-Aufruf mit Deadline: nach 500 ms gibt der Client auf

    .withDeadlineAfter(500, TimeUnit.MILLISECONDS)
    .holeStatus(anfrage);
System.out.println(antwort.getStatus() + ", noch " + antwort.getEtaMinuten() + " min");

// Server-Streaming: ein Iterator, der neue Positionen liefert

while (positionen.hasNext()) {
  Position p = positionen.next();
  karte.zeige(p.getBreite(), p.getLaenge());
}

Wann gRPC statt REST? Für Aufrufe zwischen eigenen Diensten mit viel Last, kurzen Antwortzeiten, mehreren Programmiersprachen oder Streaming. Für eine öffentliche API, die Partner mit curl, Browser oder beliebigen Werkzeugen nutzen, bleibt REST meist besser: lesbar, überall unterstützt, gut zu cachen. Browser können gRPC nicht direkt sprechen, sie brauchen gRPC-Web und einen Proxy.

gRPC ist trotz Streaming eine synchrone Verbindung im Sinn dieser Station: Beide Seiten müssen gleichzeitig laufen. Ein Stream ist kein Broker und puffert nichts für später.

GraphQL in einem Absatz

GraphQL ist eine Abfragesprache für APIs. Es gibt nur eine Adresse, meist POST /graphql. Der Client schreibt genau hin, welche Felder er will, auch über mehrere Objekte hinweg. Er bekommt nicht zu viel (overfetching) und muss nicht fünfmal nachfragen (underfetching). Das passt gut für Apps mit vielen verschiedenen Bildschirmen. Nachteile: HTTP-Caching ist schwieriger, und teure Abfragen müssen begrenzt werden.

query {
  bestellung(id: "B-4711") {
    status
    restaurant { name }
    kurier { vorname position { breite laenge } }
  }
}

Schritt 6 · Messaging

Queue oder Topic: Wer bekommt die Nachricht?

Bei asynchroner Kommunikation steht ein Message Broker zwischen den Diensten. Er kennt zwei Grundmuster:

  • Point-to-Point mit Queue: Jede Nachricht bekommt genau ein Empfänger. Mehrere Empfänger an derselben Queue teilen sich die Arbeit (competing consumers). Beispiel: 300 Druckaufträge für Etiketten, drei Drucker-Worker.
  • Publish/Subscribe mit Topic: Jeder Abonnent bekommt eine eigene Kopie. Der Sender weiss nicht, wie viele zuhören. Beispiel: «BestellungAufgegeben» interessiert Küche, Kurier und Benachrichtigung.

Ausprobieren: Nachrichten verschicken

Drück auf «Nachricht senden». Sende mehrere Nachrichten und vergleiche die Zähler.

Was du sehen solltest: Bei der Queue zählen die drei Worker zusammen so viele Nachrichten, wie du gesendet hast. Beim Topic zählt jeder Abonnent alle. Ist ein Abonnent offline, hält der Broker seine Kopien zurück und liefert sie nach, sobald er wieder läuft. Das ist zeitliche Entkopplung.

RabbitMQ und Kafka: zwei verschiedene Ideen

Beide sind Message Broker, aber sie speichern Nachrichten ganz verschieden.

So funktioniert Kafka im Detail:

  • Ein Topic ist in Partitionen aufgeteilt. Der Producer gibt jedem Event einen Schlüssel mit, zum Beispiel die Bestell-ID. Gleicher Schlüssel = gleiche Partition = Reihenfolge bleibt erhalten. Alle Events zu B-4711 kommen also in der richtigen Reihenfolge an.
  • In einer Consumer Group liest jede Partition genau ein Consumer. Innerhalb der Gruppe verhält sich das Topic also wie eine Queue: Die Arbeit wird geteilt.
  • Verschiedene Gruppen lesen unabhängig voneinander alles. Zwischen Gruppen verhält sich das Topic wie Publish/Subscribe.
  • Kafka löscht nicht beim Lesen, sondern erst nach der Retention. Ein neuer Dienst kann darum die Events der letzten Tage nachlesen.
Falle: Mehr Consumer als Partitionen bringen nichts. Ein Topic mit 3 Partitionen und eine Gruppe mit 5 Consumern: Nur 3 arbeiten, 2 warten untätig. Die Zahl der Partitionen begrenzt die Parallelität einer Gruppe.
Falle: Kafka garantiert die Reihenfolge nur innerhalb einer Partition, nicht über das ganze Topic. Haben «BestellungAufgegeben» und «BestellungStorniert» verschiedene Schlüssel, kann das Storno zuerst ankommen.
Wie baust du Publish/Subscribe mit RabbitMQ?

Der Producer schickt an einen Exchange vom Typ fanout (oder topic mit Routing-Mustern). Jeder Abonnent hat eine eigene Queue, die an den Exchange gebunden ist. Der Exchange legt eine Kopie in jede gebundene Queue. Innerhalb jeder Queue gilt wieder Point-to-Point.

Code: Kafka-Producer und -Consumer in TypeScript

Mit der Bibliothek kafkajs für Node.js. Der Bestellservice schreibt, die Küche liest in ihrer Consumer Group.

import { Kafka } from "kafkajs";

const kafka = new Kafka({ clientId: "bestellservice", brokers: ["kafka:9092"] });
const producer = kafka.producer();
await producer.connect();

export async function bestellungAufgegeben(b: Bestellung) {
  await producer.send({
    topic: "bestellungen",
    messages: [{
      key: b.id,                     // gleiche Bestellung → gleiche Partition
      value: JSON.stringify({ id: crypto.randomUUID(), type: "BestellungAufgegeben", data: b }),
    }],
  });
}
const consumer = kafka.consumer({ groupId: "kueche" });
await consumer.connect();
await consumer.subscribe({ topics: ["bestellungen"] });

await consumer.run({
  eachMessage: async ({ partition, message }) => {
    const event = JSON.parse(message.value!.toString());
    if (await schonVerarbeitet(event.id)) return; // Duplikat: idempotent bleiben
    await kochauftragAnlegen(event.data);
    await alsVerarbeitetMerken(event.id);
    // Offset wird erst nach erfolgreichem Durchlauf bestätigt → at-least-once
  },
});

Schritt 7 · Zustellgarantien

Kommt die Nachricht an, und wie oft?

Ein Consumer kann abstürzen, nachdem er eine Nachricht verarbeitet, aber bevor er das bestätigt hat. Oder davor. Je nachdem, wann bestätigt wird, gibt es drei Garantien:

GarantieWieFolgePasst für
at-most-once
höchstens einmal		zuerst bestätigen, dann verarbeiten; kein Retrykann verloren gehen, nie doppeltKurierposition jede Sekunde: eine fehlt, egal
at-least-once
mindestens einmal		zuerst verarbeiten, dann bestätigen; bei Fehler nochmalsgeht nie verloren, kann doppelt kommenStandard für Bestellungen und Zahlungen, zusammen mit idempotentem Consumer
exactly-once
genau einmal		Transaktionen über Lesen, Verarbeiten und Schreibengenau einmal, aber aufwendigKafka-intern (Kafka Streams, Transaktionen)

Exactly-once über Systemgrenzen hinweg, etwa Kafka plus eine fremde Zahlungs-API, gibt es nicht gratis. In der Praxis kombiniert man darum at-least-once mit einem idempotenten Consumer: Jedes Event hat eine eindeutige ID. Der Consumer merkt sich die verarbeiteten IDs und ignoriert Duplikate. Das Ergebnis wirkt wie «genau einmal».

{
  "specversion": "1.0",
  "id": "e7a1c2d4-5b6f-4e8a-9c0d-1f2e3a4b5c6d",
  "type": "BestellungAufgegeben",
  "source": "/bestellservice",
  "time": "2026-11-01T18:42:07Z",
  "subject": "B-4711",
  "data": { "bestellId": "B-4711", "restaurantId": "R-12", "total": 34.50 }
}
Falle: «Wir nutzen Kafka, also ist alles exactly-once.» Nein. Kafka bietet exactly-once nur für Abläufe, die von Kafka lesen und nach Kafka schreiben. Belastet dein Consumer eine Kreditkarte über eine fremde API, musst du Duplikate selbst abfangen.

Schritt 9 · Zugang und Adressen

API-Gateway, Backend for Frontend und Service Discovery

Ein API-Gateway ist die einzige Eingangstür für alle Clients. Wie der Empfang in einem Spital: Er prüft den Ausweis und schickt dich in die richtige Abteilung. Die Clients kennen nur das Gateway, nicht die Dienste dahinter. Typische Aufgaben:

  • Routing: /api/bestellungen/** geht an den Bestellservice, /api/restaurants/** an den Katalogservice.
  • Authentifizierung: Token prüfen, bevor eine Anfrage ins Innere darf. Ohne gültiges Token: 401.
  • Rate Limiting: höchstens so viele Anfragen pro Minute und Client, sonst 429. Schützt vor Überlast und Missbrauch.
  • Ausserdem oft: TLS beenden, Protokolle übersetzen, Antworten zwischenspeichern, Zugriffe protokollieren.

Ein Backend for Frontend (BFF) ist ein eigenes kleines Backend pro Client-Art. Die Web-App will eine reichhaltige Seite, die Mobile-App eine schlanke Antwort für langsames Netz. Statt einer API, die allen ein bisschen passt, bekommt jede Client-Art ihr eigenes BFF. Meist gehört es dem Team, das auch den Client baut.

spring:
  cloud:
    gateway:
      routes:
        - id: bestellungen
          uri: lb://bestellservice        # Name statt IP: Service Discovery
          predicates:
            - Path=/api/bestellungen/**
          filters:
            - name: RequestRateLimiter    # zu viele Anfragen → 429
              args:
                redis-rate-limiter.replenishRate: 10
                redis-rate-limiter.burstCapacity: 20

Service Discovery: Wo läuft der Dienst gerade?

In der Cloud starten und stoppen Instanzen laufend. Ihre IP-Adressen ändern sich. Darum schreibt man keine Adressen fest in den Code, sondern fragt ein Verzeichnis, die Service Registry. Jede Instanz meldet sich beim Start dort an und wird entfernt, wenn ihr Gesundheitscheck (health check) scheitert.

AblaufDer Aufrufer fragt die Registry nach allen Adressen und wählt selbst eine Instanz aus.Der Aufrufer ruft einen festen Namen auf. Ein Load Balancer oder die Plattform sucht die Instanz.

Falle: Gateway und BFF nicht verwechseln. Das Gateway ist eines für alle und kümmert sich um Querschnittsthemen wie Anmeldung und Rate Limiting. Ein BFF gibt es pro Client-Art, und es formt Daten für genau diesen Client.

Sitzt es?

Das Wichtigste auf einen Blick

  • Synchron = der Aufrufer wartet, beide müssen gleichzeitig laufen (REST, gRPC). Asynchron = Nachricht an einen Broker, der Empfänger verarbeitet später.
  • REST: Ressourcen als Nomen, Aktion im HTTP-Verb, Ergebnis im Statuscode. GET, PUT, DELETE sind idempotent, POST nicht. 401 = nicht angemeldet, 403 = nicht berechtigt.
  • gRPC für schnelle interne Aufrufe und Streaming, REST für öffentliche APIs, GraphQL, wenn der Client die Felder wählen soll.
  • Queue = genau ein Empfänger pro Nachricht, Topic = jeder Abonnent bekommt eine Kopie. Kafka ist ein Log mit Partitionen, Consumer Groups und Retention.
  • At-least-once plus idempotenter Consumer (Event-ID merken) ist der Standard gegen verlorene und doppelte Nachrichten.
  • Beim Modellieren liefern Substantive die Bausteine und Verben die Verbindungsart: «fragt» = synchron, «veröffentlicht», «abonniert» = asynchron, «speichert» = Daten.
