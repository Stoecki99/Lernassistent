EDA und Message Broker: Nachrichten statt Anrufe

In einer ereignisgesteuerten Architektur (EDA) schicken Systeme einander Nachrichten und warten nicht auf eine Antwort. Ein Message Broker nimmt die Nachrichten an, bewahrt sie auf und stellt sie zu. Hier lernst du, wann das besser ist als ein synchroner Aufruf, welche Zustellmuster, Protokolle und Produkte es gibt, wie eine elektronische Nachricht aufgebaut ist und wie du Sender, Broker und Receiver im UML-Komponentendiagramm modellierst.

Hinweis: Eigene Erklärungen und Beispiele auf Basis der Modulunterlagen, nicht vom Dozenten bestätigt. Alle Firmen und Fälle sind erfunden.

Schritt 2 · Zeitliche Kopplung

Synchron oder asynchron: Wer wartet auf wen?

Synchron heisst: Der Aufrufer schickt eine Anfrage und wartet, bis die Antwort da ist (Request/Response, z. B. REST). Beide Systeme müssen gleichzeitig laufen. Das nennt man zeitliche Kopplung. Hängen mehrere synchrone Aufrufe hintereinander, wartet am Ende die ganze Kette auf das langsamste oder ausgefallene Glied.

Asynchron heisst: Der Sender gibt eine Nachricht beim Broker ab und arbeitet sofort weiter. Der Empfänger holt sie ab, wenn er bereit ist. Fällt er aus, stauen sich die Nachrichten im Broker. Es geht nichts verloren, und sobald der Empfänger zurück ist, arbeitet er den Stau ab.

Labor: Fällt der Versand aus, was passiert mit der Bestellung?

Wähle die Kommunikationsart, schick ein paar Bestellungen und lass dann den Versanddienst ausfallen. Vergleiche die Zähler.

0Bestellungen angenommen
0Fehlermeldungen an Kundin
0warten im Broker
0Pakete versandt

Bereit. Modus: synchrone Kette.

Merke: Asynchron ist nicht schneller. Die Arbeit wird nur später erledigt. Der Gewinn ist die lose Kopplung: Sender und Empfänger müssen nicht gleichzeitig laufen, und ein Ausfall reisst die anderen nicht mit.

Falle: «Asynchron» heisst nicht «ohne Broker». Schickt ein Dienst eine Nachricht direkt an einen anderen (z. B. per HTTP ohne auf die Antwort zu warten) und der Empfänger ist weg, ist die Nachricht verloren. Erst der Broker mit Persistenz macht sie sicher.
Schritt 3 · Entscheiden

Wann asynchron, wann synchron?

Asynchron passt, wenn …

  • der Sender keine sofortige Antwort braucht (Bestätigung «angenommen» genügt),
  • Empfänger zeitweise nicht verfügbar sind (Wartung, Nachtbetrieb, Partner im Ausland),
  • Lastspitzen geglättet werden sollen: Die Queue puffert, der Empfänger arbeitet im eigenen Tempo,
  • viele Empfänger dasselbe Ereignis brauchen und neue dazukommen sollen, ohne den Sender zu ändern,
  • Arbeit parallel auf mehrere Worker verteilt werden soll,
  • typisch: Microservices untereinander, IoT-Geräte, B2B-Austausch, Anbindung von ERP-Systemen wie SAP.

Synchron passt, wenn …

  • die Antwort sofort gebraucht wird, um weiterzumachen (Preis, Verfügbarkeit, Login),
  • der Benutzer auf dem Bildschirm auf das Ergebnis wartet,
  • es eine Abfrage ist, die nichts verändert (lesen),
  • Einfachheit wichtiger ist als Ausfallsicherheit: kein Broker, den man betreiben muss.

Synchrone APIs (REST, SOAP, GraphQL, gRPC) behandelt Station 2.

Schritt 5 · Zwei Familien

Klassische MOM oder Event Streaming?

Es gibt zwei Bauarten von Brokern. Eine klassische MOM (z. B. RabbitMQ, IBM MQ, Azure Service Bus) ist eine Poststelle: Eine Nachricht wird zugestellt, bestätigt und dann gelöscht. Eine Event-Streaming-Plattform (z. B. Apache Kafka) ist eher ein Tagebuch: Jede Nachricht wird hinten an ein Log angehängt und bleibt dort für eine eingestellte Zeit. Jede Lesergruppe (Consumer Group) merkt sich ihre Position, den Offset. Neue Leser können von vorne lesen (Replay).

Schritt 6 · Nachrichtentypen

Event oder Command?

Event: «Es ist passiert»

Meldet eine Tatsache. Der Sender weiss nicht und muss nicht wissen, wer reagiert. Name in der Vergangenheit: «BestellungAufgegeben», «PatientAufgenommen». Typisch über ein Topic an beliebig viele Abonnenten.

{
  "id": "7f3c9a10-2b4e-4d61-9f0a-1c2d3e4f5a6b",
  "typ": "BestellungAufgegeben",
  "zeit": "2026-11-02T09:15:00Z",
  "daten": { "bestellNr": "B-1042", "total": 48.60 }
}

Command: «Tu das»

Ist ein Auftrag an genau einen zuständigen Empfänger. Der Sender erwartet, dass es erledigt wird. Name im Imperativ: «RechnungVersenden», «PaketAnmelden». Typisch über eine Queue.

{
  "id": "0d9e8f7a-6b5c-4d3e-8f2a-1b0c9d8e7f6a",
  "typ": "RechnungVersenden",
  "antwortAn": "rechnung.status",
  "daten": { "bestellNr": "B-1042", "kanal": "E-Mail" }
}
Falle: Ein «Event» im Imperativ («SendeMail») ist in Wahrheit ein Command. Der Sender legt damit fest, was der Empfänger tun soll, und koppelt sich fachlich an ihn. Prüfe den Namen: Vergangenheit = Event, Befehl = Command.
Schritt 7 · Doppelt zugestellt

Idempotenz: Wenn die Nachricht zweimal kommt

Ein Broker garantiert meist at-least-once: Die Nachricht kommt sicher an, im Fehlerfall aber auch zweimal. Das passiert zum Beispiel, wenn der Empfänger die Nachricht verarbeitet hat, aber abstürzt, bevor seine Bestätigung beim Broker ankommt. Der Broker stellt dann nochmals zu. Darum muss der Empfänger idempotent sein: Zweimal verarbeiten darf nicht zwei Rechnungen ergeben.

ZustellgarantieWieFolgePasst für
at-most-oncezuerst bestätigen, dann verarbeitenkann verloren gehen, nie doppeltMesswerte jede Sekunde, Log-Einträge
at-least-oncezuerst verarbeiten, dann bestätigen; bei Fehler nochmalsgeht nie verloren, kann doppelt kommenStandard für Bestellungen, Rechnungen, Zahlungen (mit Idempotenz)
exactly-onceTransaktionen über Lesen, Verarbeiten und Schreibengenau einmal, aber aufwendig und nur innerhalb eines Systemsz. B. Kafka-intern (Kafka Streams)

Spiel beide Abläufe ab: zuerst ohne Idempotenz, dann mit einer Tabelle der verarbeiteten Nachrichten-IDs.

So wird ein Empfänger idempotent

  • Nachrichten-ID merken: Jede Nachricht trägt eine eindeutige ID. Der Empfänger speichert verarbeitete IDs und ignoriert Wiederholungen.
  • Fachlicher Schlüssel: Rechnungsnummer = Bestellnummer, die Datenbank lehnt ein zweites Mal ab (Unique-Constraint).
  • Zustand setzen statt ändern: «Status = bezahlt» ist idempotent, «Saldo + 50» nicht.
  • Duplikaterkennung im Broker: Manche Broker (z. B. Azure Service Bus) verwerfen Duplikate mit gleicher Message-ID innerhalb eines Zeitfensters.

Code: idempotenter Receiver (Node.js)

async function verarbeite(msg) {
  const id = msg.properties.messageId;
  if (await db.verarbeitet.exists(id)) {
    kanal.ack(msg);            // Duplikat: bestätigen, nichts tun
    return;
  }
  await db.transaktion(async (tx) => {
    await rechnungErstellen(tx, JSON.parse(msg.content));
    await tx.verarbeitet.insert(id);   // gleiche Transaktion
  });
  kanal.ack(msg);              // erst jetzt löscht der Broker
}

Schritt 9 · Protokolle

AMQP, Kafka, MQTT, JMS: wofür und warum

Das Protokoll legt fest, wie Sender und Empfänger mit dem Broker sprechen. Im Komponentendiagramm steht es an der Verbindung zum Broker und am Ball (bereitgestellte Schnittstelle) des Brokers.

Falle: JMS (Jakarta Messaging) ist genau genommen kein Drahtprotokoll, sondern eine Java-Programmierschnittstelle. Was über die Leitung geht, bestimmt der Broker (z. B. TIBCO EMS oder IBM MQ). Darum spricht ein Python- oder .NET-Programm nicht «JMS». Im Diagramm einer Jakarta-EE-Anwendung beschriftest du die Verbindung zum Broker trotzdem mit «JMS», so wie im Referenzmodell.

Code: RabbitMQ über AMQP (Node.js, skriptbasiert)

Der Sender Adapter der Velo-Werkstatt «Speiche» meldet einen abgeschlossenen Reparaturauftrag. Der Receiver Adapter der Buchhaltung holt ihn ab. Bibliothek: amqplib.

import amqp from "amqplib";
import { randomUUID } from "node:crypto";

const verbindung = await amqp.connect("amqp://broker.speiche.example:5672");
const kanal = await verbindung.createConfirmChannel();
await kanal.assertExchange("werkstatt", "topic", { durable: true });

export async function auftragAbgeschlossen(auftrag) {
  const event = { id: randomUUID(), typ: "AuftragAbgeschlossen",
                  auftragNr: auftrag.nr, betrag: auftrag.total };
  kanal.publish("werkstatt", "auftrag.abgeschlossen",   // Routing Key
    Buffer.from(JSON.stringify(event), "utf8"),
    { persistent: true, messageId: event.id, contentType: "application/json" });
  await kanal.waitForConfirms();   // Broker hat übernommen
}
await kanal.assertQueue("buchhaltung.auftraege", { durable: true,
  arguments: { "x-dead-letter-exchange": "werkstatt.dlx" } });
await kanal.bindQueue("buchhaltung.auftraege", "werkstatt", "auftrag.*");
kanal.prefetch(1);                         // eine Nachricht aufs Mal

kanal.consume("buchhaltung.auftraege", async (msg) => {
  try {
    await buchen(JSON.parse(msg.content.toString("utf8")));
    kanal.ack(msg);                     // erledigt: Broker löscht
  } catch (fehler) {
    kanal.nack(msg, false, false);       // nicht nochmals: ab in die Dead Letter Queue
  }
});

public class AustrittReceiverAdapter implements MessageListener {

  @EJB private Einsatzplanung einsatzplanung;    // Session Bean im Business Logic Layer

  @Override

      throw new EJBException(e);   // Rollback: der Broker stellt erneut zu

Schritt 11 · Nachricht in drei Ebenen

Die elektronische Nachricht als Zwiebel

Damit zwei Systeme einander verstehen, müssen sie sich auf drei Ebenen einig sein. Innen steht die Semantik (was bedeutet der Inhalt?), darum herum das Format (wie ist er strukturiert?), aussen die Codierung (wie werden Zeichen zu Bytes?). Tippe eine Schicht an.

Semantik: Was bedeutet die Nachricht?

Eine semantische Norm legt fest, welche Felder eine Bestellung, Rechnung oder Laborbefund hat und was jedes Feld bedeutet. Erst damit weiss der Empfänger, dass ein bestimmtes Feld «zu zahlender Betrag» heisst.

Das Format legt die Syntax fest: Wo beginnt ein Feld, wie werden Felder verschachtelt? Dieselbe Bestellposition in drei Formaten:

Codierung: Wie werden Zeichen zu Bytes?

Die Codierung (Zeichensatz) bestimmt, welches Byte für welches Zeichen steht. Sind sich Sender und Empfänger hier nicht einig, wird aus «Müller» Zeichensalat.

CodierungMüller

  • UTF-8: internationaler Standard, alle Zeichen der Welt, ASCII-Zeichen bleiben 1 Byte. Standard für XML und JSON.
  • ASCII: nur 128 Zeichen (westliche Buchstaben ohne Umlaute), alte Schnittstellen, EDI-Dateien.
  • EBCDIC: Zeichensatz der IBM-Grossrechner (Mainframe). Ganz andere Bytes, darum muss bei der Anbindung umgewandelt werden.

Schritt 12 · Schnittstelle beschreiben

AsyncAPI und die Schnittstellentabelle

Synchrone REST-APIs beschreibst du mit OpenAPI. Für asynchrone Schnittstellen gibt es AsyncAPI: eine YAML- oder JSON-Datei, die Server (Broker und Protokoll), Kanäle (Queues, Topics), Operationen (send, receive) und den Aufbau der Nachrichten festhält. Daraus lassen sich Dokumentation und Code erzeugen.

asyncapi: 3.0.0
info:
  title: Werkstatt-Ereignisse Speiche
  version: 1.0.0
servers:
  produktion:
    host: broker.speiche.example:5672
    protocol: amqp                     # Protokoll an der Verbindung
channels:
  auftragAbgeschlossen:
    address: auftrag.abgeschlossen       # Routing Key im Exchange «werkstatt»
    messages:
      auftragAbgeschlossen:
        $ref: '#/components/messages/AuftragAbgeschlossen'
operations:
  meldeAuftragAbgeschlossen:
    action: send                        # Speiche ist Sender
    channel:
      $ref: '#/channels/auftragAbgeschlossen'
components:
  messages:
    AuftragAbgeschlossen:
      name: AuftragAbgeschlossen         # Event: Vergangenheit
      contentType: application/json    # Format, Codierung UTF-8
      payload:
        type: object
        required: [id, auftragNr, betrag]
        properties:
          id:        { type: string, format: uuid }   # für Idempotenz
          auftragNr: { type: string }
          betrag:    { type: number }
          waehrung:  { type: string, default: CHF }

Schritt 13 · Vom Text zum Modell

Eine asynchrone Verbindung Schritt für Schritt modellieren

Lies den Satz und geh die Schritte durch. Jeder Teil des Satzes verrät eine Entscheidung im Modell. Fahr mit der Maus über einen markierten Satzteil: Das passende Modellteil leuchtet mit.

Regeln für asynchrone Verbindungen im Komponentendiagramm

  1. Signalwörter suchen: «meldet», «sendet», «veröffentlicht», «abonniert», «ohne zu warten», «später», «auch wenn … nicht läuft» = asynchron. «fragt ab», «ruft auf», «braucht sofort» = synchron.
  2. Über den Broker: Alle asynchronen Verbindungen laufen über einen Message Broker im Paket MOM. Der Broker bietet einen Ball mit dem Protokoll an (z. B. AMQP).
  3. Receiver und Sender getrennt: Im eigenen System hängen ein Receiver Adapter und ein Sender Adapter im Async Communication Layer, je mit dem Stereotyp der Technologie («C#», «EJB MDB», «JS»).
  4. Umsysteme konkret: Wer asynchron mit dir verbunden ist, steht im Paket «async connected Systems» und hängt ebenfalls am Broker.
  5. Beschriften: Protokoll an jede Verbindung zum Broker, bei Bedarf Format und Semantik («AMQP · UBL»).
  6. Muster wählen: ein Empfänger = Queue, mehrere gleichartige = Worker Queue, alle Interessierten = Topic, Antwort nötig = Request-Reply.
Falle 1: Integration Middleware statt Broker. Asynchrone Verbindungen gehören an den Message Broker, nicht an die Integration Middleware und nicht an ein API-Gateway.
Falle 2: Ein gemeinsamer «async Adapter». Im Referenzkatalog stehen Receiver und Sender zusammengefasst; im konkreten Fall zeichnest du sie als zwei Komponenten, weil sie verschieden ausgelöst werden (Receiver vom Broker, Sender von der Fachlogik).
Falle 3: Topic für Aufträge. Soll jeder Auftrag nur einmal ausgeführt werden, brauchst du eine Queue. Mit einem Topic erhielte jeder Abonnent den Auftrag, und er würde mehrfach erledigt.
Schritt 14 · EDA in der Gesamtarchitektur

Wo Broker und Adapter im Komponentendiagramm stehen

So erscheint asynchrone Kommunikation in den Referenzarchitekturen des Moduls. Erstens in der monolithischen Mehrschichtenarchitektur: Im Business Tier gibt es einen Async Communication Layer mit Receiver und Sender Adapter. Der Broker steht rechts im Paket MOM, die asynchron verbundenen Systeme darunter. Das vertiefst du in Station 7 (serverseitige Architekturen).

Zweitens in der Makroarchitektur mit Microservices (Variante 2, «async coupled Microservices»): Im Docker Host verbindet ein eigener Docker Host MQ die Microservices untereinander. Umsysteme erreicht nur der Driven Adapter Service, und zwar über den externen Broker im Paket MOM. Das vertiefst du in Station 5.

Merke: In der Makroarchitektur zeichnest du den Broker (MOM), aber kein API-Gateway und keine Integration Middleware. In der Mehrschichtenarchitektur zeichnest du die unmittelbaren Umsysteme konkret, den Broker im Paket MOM und je einen Receiver und Sender Adapter.

Σ Merksätze

Auf einen Blick

  • Asynchron entkoppelt zeitlich: Der Sender wartet nicht, der Broker puffert, ein Ausfall des Empfängers staut Nachrichten statt eine Kaskade auszulösen.
  • Der Message Broker ist die Poststelle: Queue (ein Empfänger), Topic (alle Abonnenten), Exchange (Verteilung), Persistenz (überlebt Neustart), Bestätigung (erst nach ack löschen).
  • Event = Tatsache in der Vergangenheit, meist über ein Topic; Command = Auftrag im Imperativ, meist über eine Queue. Bei at-least-once muss der Empfänger idempotent sein.
  • Zustellmuster: Fire-and-Forget, Request-Reply (Antwort-Queue, Correlation-ID), Queue, Worker Queue, Topic.
  • Protokolle: AMQP allgemein (RabbitMQ, Azure Service Bus), Kafka für Event Streaming mit Replay, MQTT leichtgewichtig für IoT, JMS in Jakarta EE (TIBCO EMS, IBM MQ).
  • Nachricht in drei Ebenen: Semantik (EDIFACT, HL7, IDoc, UBL, ISO 20022), Format (XML, JSON, CSV), Codierung (UTF-8, ASCII, EBCDIC); beschrieben mit AsyncAPI.
  • Im Diagramm: Broker im Paket MOM mit Protokoll-Ball, Receiver und Sender Adapter getrennt im Async Communication Layer, jede Verbindung beschriftet.
