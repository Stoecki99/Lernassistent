Clientseitige Architekturen

Alles, was der Mensch sieht und anfasst, läuft auf einem Client: im Browser, als App auf dem Handy, als Desktop-Programm oder sogar in Excel. Hier lernst du, welche Client-Typen es gibt, was jeweils auf dem Gerät und was auf dem Server läuft, und wie du in der Prüfung den Client Tier einer Architektur richtig ergänzt: welche App, welche Technologie, welche Schnittstelle, und warum.

Hinweis: Eigene Erklärungen und Beispiele auf Basis der Modulunterlagen, nicht vom Dozenten bestätigt. Alle Firmen und Fälle sind erfunden.

  • Die wichtigsten Client-App-Technologien erklären: Bildschirmdesign, LBS, AR, Offline/Online/Sync, MVC, MVVM, AJAX.

Schritt 0 · Ohne Vorwissen

Sechs Bausteine mit Alltagsbildern

Ein verteiltes System hat immer zwei Seiten: den Client, mit dem ein Mensch arbeitet, und den Server, der Daten und Fachlogik hält. Spannend ist, wie viel Arbeit auf welcher Seite passiert. Stell dir ein Restaurant vor.

Client = Gast

Der Gast bestellt und isst. Er kocht nicht selbst. Der Client zeigt an, nimmt Eingaben an und schickt Anfragen an den Server.

Server = Küche

Die Küche hat die Vorräte (Daten) und die Rezepte (Fachlogik). Sie beantwortet Bestellungen vieler Gäste gleichzeitig.

Thin oder Rich Client

Fertiger Teller (thin): Die Küche macht alles. Fondue am Tisch (rich): Ein Teil der Arbeit passiert beim Gast.

Browser = Theaterbühne

Die Bühne spielt jedes Stück, egal wer es geschrieben hat. Der Browser führt jede Web App aus, auf jedem Gerät und Betriebssystem.

Installierbare App = eigenes Werkzeug

Ein Werkzeug, das genau zu deinem Gerät passt. Du musst es zuerst holen (App Store, Installer), dafür kann es alles, was das Gerät kann.

Schnittstelle = Durchreiche

Gast und Küche reden über ein vereinbartes Fenster. In der Architektur heisst es HTTP, REST, GraphQL oder OData.

Kurz üben: Läuft im Browser oder wird installiert?

Achte darauf, wo das Programm ausgeführt wird, nicht darauf, wie es aussieht.

Schritt 2 · Devices und Betriebssysteme

HCI, Client Devices und Client-OS

HCI fragt: Wie arbeitet ein Mensch mit dem Computer? Eingabe über Tastatur, Maus, Touch, Stimme oder Gesten, Ausgabe über Bildschirm, Ton und Vibration. Das Gerät bestimmt, welche Eingabe und Ausgabe möglich ist, und damit auch, welche Client-App sinnvoll ist.

Mobile Devices

Smartphone, Tablet, Notebook.

  • Touch, Kamera, GPS, Sensoren
  • Akku, wechselndes Netz, Funklöcher
  • kleiner Bildschirm, kurze Sitzungen

Stationäre Devices

Desktop-PC, Workstation.

  • grosse Bildschirme, Maus und Tastatur
  • stabiles Netz, viel Rechenleistung
  • lange Arbeitssitzungen, voller Funktionsumfang

Wearables

Smartwatch, Fitnessband, Datenbrille.

  • sammeln Daten über Sensoren
  • tauschen Daten aus (oft über das Handy)
  • informieren über Display, Ton oder Haptik

Achtung: Energie, Tragekomfort und Reichweite sind knapp. Beispiel: Eine Smartwatch zeigt Pflegenden den nächsten Patientenruf und vibriert.

IoT-Device

Ein «smartes Ding»: Embedded System mit Chip, Sensoren und Aktoren im physischen Kontext, verbunden mit einer IoT-Plattform.

Beispiele: Velo-Schloss, das per App öffnet; Briefkasten, der «Post da» meldet; Produktionsmaschine, die ihren Zustand sendet.

VDI

Der ganze Desktop läuft als virtuelle Maschine im Rechenzentrum. Auf dem Gerät läuft nur ein View Client, der das Bild zeigt und Eingaben zurückschickt.

Gut für zentrale Verwaltung und Sicherheit, aber ohne Netz geht nichts.

VDI als Diagramm: Wo läuft der Desktop?

Bildschirmdesign, Standort, AR und Serverzugang

Bildschirmdesign: vier Strategien

Die gleiche Oberfläche muss auf 360 px und auf 1280 px funktionieren. Es gibt vier Strategien: eine fixe Grösse, mehrere fixe Grössen je Kontext (z. B. eine eigene Mobile-Seite), alles skalieren oder Responsive Design. Wähle eine Strategie und verändere die Gerätebreite.

390 px

Merke: Responsive Design ist heute Standard. Skalieren klappt für Bilder und Zeichnungen, bei Schrift nur bedingt: Sie wird unlesbar klein.

Location Based Services (LBS)

Ein LBS nutzt Standorte. Zwei Positionen spielen mit: die des mobilen Geräts und die des Ziels. Jede kann ermittelt, vorgegeben oder egal sein. Regel: Mindestens ein Standort wird ermittelt, sonst ist es kein LBS.

Schritt 5 · Architektur- und Entwurfsmuster

MVC, MVVM und AJAX

Muster trennen Darstellung, Steuerung und Daten. Das macht Oberflächen testbar und austauschbar. Zwei Muster brauchst du: MVC (typisch serverseitig, z. B. ASP.NET MVC) und MVVM (typisch in installierten Apps mit Data Binding, z. B. .NET MAUI mit XAML).

MVC in ASP.NET: Formular absenden

Tippe Controller, View und Model an. Spiel den Ablauf ab: Der Browser bekommt am Schluss fertiges HTML.

MVVM in einer MAUI-App: Data Binding

Die View (XAML) kennt nur Eigenschaften des ViewModels. Ändert sich ein Wert im ViewModel, zeichnet sich die View selbst neu. Das ViewModel kennt die View nicht.

AJAX: Daten nachladen, ohne die Seite neu zu laden

Klassisch schickt der Browser bei jedem Klick eine Anfrage und bekommt eine ganze neue Seite. Mit AJAX ruft ein Skript im Hintergrund das Web API auf, bekommt nur Daten (heute meist JSON statt XML) und ändert einen Teil der Seite. Die Seite bleibt bedienbar, während die Antwort unterwegs ist.

// abo.js: AJAX-Aufruf an das Web API, Antwort ist JSON, kein HTML
async function aboPausieren(aboId, bis) {
  const antwort = await fetch("/api/abos/" + aboId + "/pause", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ bis: bis })
  });
  if (!antwort.ok) throw new Error("Nicht gespeichert (Status " + antwort.status + ")");
  return antwort.json();
}

// Nur der Statusbereich ändert sich, die Seite bleibt stehen.
aboPausieren(42, "2026-12-20")
  .then((abo) => { document.querySelector("#status").textContent = "Pausiert bis " + abo.bis; })
  .catch((e) => { document.querySelector("#status").textContent = e.message; });
Schritt 6 · Web Apps

Der Browser als Ausführungscontainer: klassisch, SPA, PWA

Eine Web App läuft im Browser. Der Browser ist dabei viel mehr als ein Anzeigeprogramm: Er ist ein Ausführungscontainer, der die App vom Gerät und vom Betriebssystem abschirmt. Darum laufen Web Apps auf jedem Gerät mit aktuellem Browser.

Ausführen

  • HTML und CSS rendern
  • JavaScript interpretieren
  • WebAssembly ausführen

Speichern

  • Cookies, IndexedDB, Cache
  • Lesezeichen und Verlauf

Verwalten und schützen

  • Tabs und Fenster
  • Sicherheitsfunktionen (Sandbox, Zertifikate)
  • Add-ons, Entwicklerwerkzeuge (F12)

Bietet dir

Geräte- und Plattformunabhängigkeit: eine Codebasis, Zugriff über eine URL, keine Installation, Updates sofort für alle.

HTML5 Web App und SPA

Eine HTML5 Web App besteht aus HTML5 (Struktur), CSS (Aussehen) und JavaScript (Logik), oft mit Hilfen wie Web Components oder Bootstrap. Die SPA geht weiter: Der Browser lädt einmal eine Seite mit allen Skripten (Initial Load). Danach ersetzt das Skript Inhalte selbst und holt nur noch Daten per AJAX. Darum hat die SPA in der Architektur zwei Verbindungen: eine zu den statischen Ressourcen und eine zum Web API.

// KistenListe.jsx: läuft im Browser, gehört zur Komponente «SPA»
import { useEffect, useState } from "react";

export function KistenListe({ plz }) {
  const [kisten, setKisten] = useState([]);
  const [fehler, setFehler] = useState(null);

  useEffect(() => {
    fetch("/api/kisten?plz=" + plz)              // AJAX an das Web API (REST · JSON)
      .then((r) => { if (!r.ok) throw new Error(r.status); return r.json(); })
      .then(setKisten)
      .catch(() => setFehler("Gerade keine Verbindung."));
  }, [plz]);                                     // neu laden, wenn die PLZ wechselt

  if (fehler) return <p role="alert">{fehler}</p>;
  return (
    <ul>
      {kisten.map((k) => <li key={k.id}>{k.name}: CHF {k.preis}</li>)}
    </ul>
  );
}

PWA: Service Worker als Proxy, Manifest und Cache

Eine PWA ist eine SPA mit drei Zusätzen. Das Manifest beschreibt Name, Icon, Start-URL und Darstellung; damit lässt sich die App auf dem Startbildschirm ablegen und startet mit Splash-Screen im Vollbild. Der Service Worker ist ein Skript, das der Browser für die PWA registriert. Er sitzt als Proxy zwischen App und Netz. Der Cache hält App-Shell und letzte Daten. Der Browser bleibt dabei als unsichtbarer Container im Hintergrund.

Schaltet HTML5 Resources und Web API aus und spielt den Ablauf «Server weg» ab.

Im Ausfall-Modus färbt die Engine PWA und Service Worker orange: Sie hängen am Server und bekommen keine frischen Daten. Der Ablauf zeigt, warum die App trotzdem läuft: Der Service Worker antwortet aus dem Cache.

Vorteile der PWA

  • installierbar mit Icon («App-Gefühl»)
  • offlinefähig dank Service Worker und Cache
  • Push-Benachrichtigungen
  • schneller durch Hintergrund-Synchronisation
  • alle Vorteile einer Web App (eine Codebasis, kein Store)

Grenzen

  • braucht einen aktuellen Browser
  • Gerätefunktionen nur so weit, wie der Browser sie freigibt
  • Funktionen je Plattform unterschiedlich (iOS ist zurückhaltender)

// In der App: navigator.serviceWorker.register("/sw.js");
const SHELL = "frischkiste-shell-v3";
const DATEIEN = ["/", "/index.html", "/app.js", "/app.css", "/icons/kiste-192.png"];

self.addEventListener("install", (e) => {            // 1. App-Shell in den Cache legen
  e.waitUntil(caches.open(SHELL).then((c) => c.addAll(DATEIEN)));
});

self.addEventListener("fetch", (e) => {              // 2. Jeder Request läuft hier durch (Proxy)
  if (e.request.method !== "GET") return;
  const url = new URL(e.request.url);
  if (url.pathname.startsWith("/api/")) {
    // Daten: zuerst das Netz; ist der Server weg, die letzte Antwort aus dem Cache
    e.respondWith(
      fetch(e.request)
        .then((r) => { const kopie = r.clone(); caches.open("daten").then((c) => c.put(e.request, kopie)); return r; })
        .catch(() => caches.match(e.request))
    );
  } else {
    // App-Shell: zuerst der Cache, darum startet die PWA schnell und auch offline
    e.respondWith(caches.match(e.request).then((r) => r || fetch(e.request)));
  }
});

Serverseitig gerendert: ASP.NET MVC, Blazor, JSF

ASP.NET MVC (Active Server Pages) rendert mit Razor (HTML und C# gemischt) nach dem MVC-Muster; das Model hat die Verbindung zur nächsten Schicht oder zur Datenbank. Blazor (Browser + Razor) baut Oberflächen aus Razor-Komponenten in zwei Varianten: Blazor Server führt den C#-Code auf dem Server aus und schickt UI-Änderungen über eine SignalR-Verbindung; Blazor WebAssembly lädt die .NET-Laufzeit als Wasm in den Browser und läuft dort, auch als PWA. Komponentenbibliotheken wie MudBlazor setzen darauf auf. JSF (Jakarta Server Faces) ist das Gegenstück in Jakarta EE: Facelets-Seiten mit Backing Beans im Web Container, die Fachlogik und die DB-Verbindung liegen in EJBs; dazu kommen oft Frameworks wie Spring.

Schritt 7 · Installierbare Apps

Single Platform, Cross-/Multiplatform und Hybrid

Installierbare Apps für Mobile oder Desktop gibt es in drei Bauarten. Sie unterscheiden sich darin, wie viele Codebasen du brauchst und wie nah die App am Betriebssystem ist. Wähle eine Bauart und sieh dir den Stapel an: oben dein Code, unten das Gerät.

Begriffe: In der Praxis werden «Cross-Platform» und «Multiplatform» oft gleich verwendet. Faustregel für diese Station: Cross-Platform heisst, eine Laufzeit (JVM, CLR) führt denselben Zwischencode auf jedem OS aus. Multiplatform heisst, ein Framework wie .NET MAUI baut aus einer Codebasis echte Apps für Android, iOS, macOS und Windows. Beide haben eine Codebasis, das ist der Unterschied zur nativen App.

Schritt 8 · Schritt für Schritt und Regeln

Vom Anwendungsfall zur Client-App

In der Prüfung liest du Anwendungsfälle und musst daraus Client-Apps ableiten. Die Signalwörter stehen im Text. Klick dich durch ein Beispiel: Jeder Satzteil führt zu einem Teil des Entscheids.

So ergänzt du den Client Tier (Regeln)

  1. User und Anwendungsfall klären: Wer arbeitet womit, wo, wie oft?
  2. Signale suchen: unbekanntes OS, keine Installation, Offline, Kamera/GPS, Push, alte Browser, bekannte Plattform, voller Funktionsumfang, Auswertung in Excel.
  3. Client-Typ wählen und in der Tabelle mit Technologie, Begründung und User festhalten. Mehrere User-Gruppen heisst oft mehrere Client-Apps.
  4. Pakete im Client Tier: «Web Apps» (Browser) und «Installierbare Apps».
  5. Schnittstelle je App: klassische Web App → HTTP der Presentation Components bzw. des Web-App-Microservice; SPA/PWA → Static HTTP der HTML5 Resources und REST/GraphQL des Web API; installierbare Apps → REST/GraphQL des Web API; Excel → OData; Blazor Server → HTTP mit SignalR.
  6. Beschriften und begründen: jede Verbindung mit Protokoll, jede App mit zwei bis drei Sätzen.
Falle 1: Native App bei unbekanntem OS. Steht im Text «eigene Geräte» oder «Betriebssystem unbekannt», scheidet eine native iOS- oder Android-App aus. Nimm eine Web App (SPA/PWA) oder eine plattformübergreifende App.
Falle 2: Teile als eigene Komponenten. Browser, Service Worker, Cache und Web-Server zeichnest du nicht als eigene Komponenten in den Client Tier. Der Service Worker ist Teil der PWA, der Web-Server ist Infrastruktur (im Paketnamen erwähnen).
Falle 3: Excel direkt an die Datenbank. Excel ist eine Client-App und nutzt die OData-Schnittstelle des Web API. Ein direkter Datenbankzugriff umgeht Fachlogik und Berechtigungen.
Falle 4: API-Gateway in der Makroarchitektur. Die Client-Apps verbindest du direkt mit Web App, HTML Resource und Web API. Ein API-Gateway gehört nicht in die Makroarchitektur.

Schritt 10 · Clients in der Makroarchitektur

Client Tier ergänzen: welche App an welche Schnittstelle

Jetzt kommen die Client-Apps ins UML-Komponentendiagramm. In der Microservices-Makroarchitektur (Variante 2) sprechen die Apps nur mit drei Microservices: dem Web-App-Microservice (HTTP, serverseitig gerendert), der HTML Resource (Static HTTP für SPA und PWA) und dem Web API (REST, GraphQL, OData). Unten das fertig modellierte Beispiel der Frischkiste. Tippe Pakete, Apps und Linien an: Jeder Steckbrief ist eine prüfungstaugliche Beschreibung.

Referenz: Client und Presentation Tier in .NET (Mehrschicht)

In der monolithischen Mehrschichtenarchitektur liegen die serverseitigen Gegenstücke der Clients im Web Tier: der Presentation Tier (Blazor Server Components über HTTP mit SignalR, Blazor-Ressourcen über Static HTTP) und der Service Tier mit dem Web API. Beide greifen nur über die Business Facade auf die Fachlogik zu.

Merke: Die Client-Apps aus der Tabelle erscheinen vollständig im Diagramm, jede mit der richtigen Assoziation. Das Web API zeigt jede angebotene Schnittstelle als eigenen Ball, z. B. REST, GraphQL und OData.

Σ Merksätze

Auf einen Blick

  • Der Client-Typ legt fest, was auf dem Gerät läuft: von View Client (VDI) und klassischer Web App (thin) bis zur installierbaren App mit lokalen Daten (rich).
  • Web Apps laufen im Browser als Ausführungscontainer: klassisch serverseitig gerendert (HTTP), SPA und PWA clientseitig (Static HTTP plus AJAX an das Web API).
  • PWA = SPA + Manifest + Service Worker als Proxy + Cache: installierbar, offlinefähig, Push. Der Service Worker ist keine eigene Komponente im Diagramm.
  • Installierbar: native (eine Plattform, beste Performance, teuer), Cross-/Multiplatform (eine Codebasis, JVM/CLR/MAUI), Hybrid (nativer Rahmen mit HTML5-Inhalt).
  • Signale lesen: unbekanntes OS und keine Installation → Web App; offline, Kamera, Push → installierbar oder PWA; alte Browser → klassische Web App; Excel → OData.
  • Im Client Tier: Pakete «Web Apps» und «Installierbare Apps», jede App mit beschrifteter Assoziation zur richtigen Schnittstelle, kein API-Gateway, keine Infrastruktur als Komponente.
