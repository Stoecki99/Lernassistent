Schritt 0 · Ohne Vorwissen

Ein Server ist wie ein Hotel

Ein Hotel bedient viele Gäste gleichzeitig, rund um die Uhr. Gäste sehen nur die Rezeption. Dahinter arbeiten Abteilungen mit klaren Aufgaben, und für Lieferanten gibt es eigene Ansprechpersonen. Genau so ist die Serverseite einer Mehrschichtenarchitektur gebaut.

Rezeption = Web Tier

Gäste am Schalter bekommen fertige Auskünfte zum Lesen (Presentation Services, HTML). Das Telefon für Reisebüros liefert nur Daten (Web API, JSON oder XML).

Concierge = Facade

Wer etwas von den Abteilungen will, geht über den Concierge. Die Business Facade ist der einzige Zugang zum Business Tier.

Abteilungen = Business Components

Küche, Housekeeping, Buchhaltung: Jede kennt ihre Regeln. Die Business Components enthalten die Geschäftslogik, je Fachgebiet eine.

Einkauf = Driven Adapter

Für jeden Lieferanten gibt es eine eigene Ansprechperson, die dessen Formulare kennt. Je Service Provider ein eigener Adapter.

Postfach = Async Layer

Briefe gehen ein und aus, ohne dass jemand am Telefon wartet. Receiver und Sender Adapter sprechen mit dem Message Broker.

Archivar = Data Access

Nur der Archivar geht ins Archiv. Die Data Access Components (DACs) sind der einzige Weg zur Datenbank.

Archiv = Data Tier

Hier liegen die Akten dauerhaft. Der Persistence/Data Tier enthält die Datenbank im DBMS.

Gebäude = Infrastruktur

Das Gebäude ist keine Abteilung. Web-Server und DBMS-Server sind keine Komponenten: Du nennst sie höchstens im Paketnamen.

Schritt 2 · Funktion und Schichten

Was ein Server tut und wie er geschichtet ist

Ein Server ist ein Programm (oder ein Rechner), das Dienste für viele Clients anbietet. Im Client-Server-Grundmuster stellt der Client eine Anfrage, der Server antwortet. In einer SOA-enabled Mehrschichtenarchitektur ist der Server zugleich Service Provider (er bietet APIs an) und Service Consumer (er nutzt APIs anderer Systeme).

1 · Anfragen annehmen

Nimmt Anfragen vieler Clients gleichzeitig an, meist über HTTP, und ordnet sie einer Sitzung zu.

2 · Präsentation oder Daten liefern

Erzeugt fertige HTML-Seiten für Menschen oder liefert Daten (JSON, XML) für Apps und Fremdsysteme.

3 · Geschäftslogik ausführen

Prüft Regeln, rechnet und steuert Vorgänge zentral an einer Stelle, für alle Clients gleich.

4 · Daten sicher speichern

Hält die Daten dauerhaft und konsistent, mit Transaktionen (alles oder nichts).

5 · Umsysteme integrieren

Ruft Service Provider synchron auf und tauscht Nachrichten asynchron über einen Message Broker aus.

6 · Querschnitt

Sicherheit (Anmeldung, Berechtigung), Protokollierung, Skalierung und Verfügbarkeit.

Die generische Mehrschichtenarchitektur

Alle drei Referenzarchitekturen folgen demselben Bauplan. Der Middle Tier hat zwei Stockwerke: Der Web Tier nimmt Anfragen an (Presentation Services für Menschen, Web API für Maschinen). Der Business Tier hat einen Eingang (Facade), die Fachlogik (Business Components) und die Driven Adapters zur Aussenwelt: Datenzugriff, synchrone Adapter zu Providern und asynchrone Adapter zum Broker. Tippe die Teile an, spiel die Abläufe ab und schalte den Ausfall-Modus ein.

Driving und Driven

Der Begriff «Driven Adapter» kommt aus der Hexagonal- oder Clean-Architektur. Driving (treibend) sind die Eingänge, die die Anwendung antreiben: Web Tier und Receiver. Driven (getrieben) sind die Ausgänge, die die Fachlogik selbst anstösst: Datenzugriff, Provider-Adapter, Sender. Die Fachlogik in der Mitte hängt von nichts Technischem ab.

Warum Web Tier und Business Tier trennen?

Beide Tiers können auf eigenen Servern laufen und unabhängig skaliert werden. Viele Seitenaufrufe brauchen mehr Web-Server, eine teure Berechnung mehr Business-Server. Die Facade mit einer klaren Schnittstelle (REST, gRPC oder RMI) macht das möglich.

Schritt 5 · Skriptbasiert

Skriptsprachen und Node.js

Skriptsprachen werden zur Laufzeit von einem Interpreter ausgeführt, nicht vorab in Maschinencode übersetzt. Das macht den Start schnell und den Code leicht änderbar. Auf dem Server sind vier Sprachen verbreitet, jede mit eigenen Frameworks.

PHP

Die klassische Sprache für Webseiten, läuft auf fast jedem Webhosting.

Frameworks: Laravel (mit Blade-Templates), Symfony, CodeIgniter · Stereotyp «PHP»

Python

Gut lesbar, stark in Datenanalyse und KI; dadurch beliebt für datennahe Webdienste.

Frameworks: Django (alles dabei), Flask, FastAPI · Stereotyp «Python»

Ruby

Auf Produktivität ausgelegt: Konvention vor Konfiguration.

Framework: Ruby on Rails · Stereotyp «Ruby»

Node.js (JavaScript)

JavaScript ausserhalb des Browsers. Ein Thread mit Event Loop bedient sehr viele gleichzeitige Anfragen.

Frameworks: express, NestJS, Fastify · Stereotyp «JS»

Aufbau von Node.js

Node.js besteht aus der JavaScript-Engine V8 (aus Chrome, übersetzt JavaScript just in time in Maschinencode), der Bibliothek libuv mit Event Loop und Threadpool sowie den Node-APIs für Dateien, Netzwerk und Prozesse. Dein JavaScript läuft in einem Haupt-Thread. Wartezeiten (Datenbank, Dateien, Netzwerk) gibt Node an das Betriebssystem oder den Threadpool ab und arbeitet sofort weiter. Ist das Ergebnis da, legt es einen Callback in die Warteschlange; die Event Loop holt ihn, sobald der Haupt-Thread frei ist. Darum ist Node.js schnell und gut skalierbar bei vielen kurzen Ein- und Ausgaben, aber schwach bei langen Berechnungen.

NPM: das Paket-Ökosystem

Der Node Package Manager verwaltet Bibliotheken (Pakete). In package.json stehen die Abhängigkeiten, npm install lädt sie. Das Ökosystem ist riesig: Für fast jedes Protokoll gibt es einen fertigen Client (AMQP, OIDC, OData). Code: RESTful Service mit express und mongoose

Ein kleines Kursangebot in vier Dateien. Jede Datei entspricht einer Komponente der skriptbasierten Referenz: Router = Web Service, Service = Business Component, Model = DAC. Testen kannst du so einen Dienst mit einem HTTP-Client wie Postman.

# wird beim Start von dotenv gelesen
PORT=3000
MONGODB_URI=mongodb://localhost:27017/kurse
const mongoose = require("mongoose");

const kursSchema = new mongoose.Schema({
  titel:   { type: String, required: true },
  start:   { type: Date, required: true },
  plaetze: { type: Number, min: 1 },
  belegt:  { type: Number, default: 0 }
});

module.exports = mongoose.model("Kurs", kursSchema);   // Dokumente in der Collection «kurs»
const Kurs = require("../models/kurs");

async function freieKurse() {
  const kurse = await Kurs.find({ start: { $gte: new Date() } }).lean();
  return kurse.filter((k) => k.belegt < k.plaetze);   // Geschäftsregel: nur Kurse mit freien Plätzen
}

async function buchen(kursId) {
  const k = await Kurs.findOneAndUpdate(
    { _id: kursId, $expr: { $lt: ["$belegt", "$plaetze"] } },   // nur, wenn noch Platz ist
    { $inc: { belegt: 1 } }, { new: true });
  if (!k) throw new Error("ausgebucht");
  return k;
}

module.exports = { freieKurse, buchen };
const express = require("express");
const service = require("../services/kursService");
const router = express.Router();

router.get("/", async (req, res, next) => {          // GET /api/kurse
  try { res.json(await service.freieKurse()); }     // Antwort als JSON
  catch (e) { next(e); }
});

router.post("/:id/buchungen", async (req, res) => {   // POST /api/kurse/42/buchungen
  try { res.status(201).json(await service.buchen(req.params.id)); }
  catch (e) { res.status(409).json({ fehler: "Kurs ist ausgebucht" }); }
});

module.exports = router;
require("dotenv").config();                          // PORT und MONGODB_URI aus .env
const express = require("express");
const mongoose = require("mongoose");

const app = express();
app.use(express.json());                              // JSON-Body lesen
app.use("/api/kurse", require("./routes/kurse"));

mongoose.connect(process.env.MONGODB_URI)             // direkte DB-Verbindung über den Treiber
  .then(() => app.listen(process.env.PORT));

Im Diagramm: Der Router ist der «JS» Web Service mit dem Ball REST, der Service eine «JS» Business Component, das mongoose-Model ein «JS» DAC mit direkter DB-Verbindung zur «DB in MongoDB». Node.js selbst ist keine Komponente: Es steht im Paketnamen, z. B. «Middle Tier – node.js Environment».

Schritt 7 · Jakarta EE

Jakarta EE: zwei Container, viele Beans

Jakarta EE (früher Java EE, heute bei der Eclipse Foundation) ist ein offener Standard für grosse Unternehmensanwendungen in Java. Er beschreibt Schnittstellen; Hersteller liefern Application Server, die ihn umsetzen: WildFly, Payara, Open Liberty, GlassFish. Dein Code läuft in Containern, die dir Transaktionen, Sicherheit, Pooling und Nebenläufigkeit abnehmen.

Web Container · Web Tier (Web-Server)
JSF Components inkl. Backing BeanSeiten für den Browser, über HTTP
RESTful Web Services (Jakarta REST)für Mobile und Desktop Apps
XML Web Services (SOAP)für Service Consumer Apps

Versteht HTTP. Ruft die Logik über die Facade per RMI auf.

EJB Container · Business Tier (Application Server)
«EJB» sync Access FacadeStateless Session Bean mit Remote-Interface (RMI)
«EJB» Business Logic ComponentsSession Beans, je Fachgebiet eine
«EJB MDB» Receiver und Sender AdapterMessage-Driven Beans mit JMS
«EJB» DACs (JPA) mit ORM-ProviderEntities und EntityManager, z. B. Hibernate
«EJB» sync Adapter je Service Providerruft REST- oder SOAP-APIs auf

Session Beans: stateless, stateful, singleton

Session Beans tragen die Geschäftslogik. Der Container entscheidet, wie viele Instanzen es gibt und welcher Client welche bekommt. Probier es aus: Wähle die Art und lass drei Clients aufrufen.

Message-Driven Bean (MDB)

Eine Bean ohne Client. Der Container ruft onMessage auf, sobald in der Queue oder im Topic eine Nachricht liegt. Viele MDB-Instanzen arbeiten parallel. Im Diagramm: Receiver Adapter «EJB MDB».

JMS (Jakarta Messaging)

Die Standard-API für Nachrichten: Queue (genau ein Empfänger) und Topic (alle Abonnenten). Broker mit JMS-Schnittstelle: ActiveMQ Artemis, TIBCO EMS, IBM MQ, RabbitMQ über ein Plugin.

JPA und ORM

Jakarta Persistence beschreibt, wie Java-Objekte (Entities) auf Tabellen abgebildet werden (Object-Relational Mapping). Der ORM-Provider, meist Hibernate oder EclipseLink, erzeugt das SQL und spricht per JDBC mit dem RDBMS.

Spring als Alternative

Spring (Spring Boot) ist kein Jakarta-Standard, sondern ein verbreitetes Framework, das Teile davon nutzt (z. B. JPA). Statt Application Server ein eingebetteter Server, statt EJB @Service-Klassen, statt MDB @JmsListener oder @RabbitListener.

Code: Session Bean als Facade

@Remote                                              // Aufruf per RMI aus dem Web Container
public interface KursFacadeRemote {
    List<KursDto> freieKurse();
    BuchungDto buchen(long kursId, long kundinId);
}

@Stateless                                           // Container hält einen Pool von Instanzen
public class KursFacade implements KursFacadeRemote {
    @EJB private KursService kurse;                   // Business Logic Component «EJB»
    @EJB private BuchungService buchungen;

    @Override
    public List<KursDto> freieKurse() { return kurse.freie(); }

    @Override
    @TransactionAttribute(TransactionAttributeType.REQUIRED)   // alles oder nichts
    public BuchungDto buchen(long kursId, long kundinId) {
        return buchungen.buchen(kursId, kundinId);
    }
}

Code: Message-Driven Bean als Receiver Adapter

@MessageDriven(activationConfig = {
    @ActivationConfigProperty(propertyName = "destinationType", propertyValue = "jakarta.jms.Queue"),
    @ActivationConfigProperty(propertyName = "destinationLookup", propertyValue = "jms/raumsperren")
})
public class RaumsperreReceiver implements MessageListener {
    @EJB private KursService kurse;

    @Override
    public void onMessage(Message nachricht) {         // der Container ruft auf, sobald eine Nachricht da ist
        try {
            String raum = nachricht.getBody(String.class);
            kurse.raumGesperrt(raum);                    // weiter an die Business-Komponente
        } catch (JMSException e) {
            throw new EJBException(e);                   // Rollback: der Broker stellt erneut zu
        }
    }
}

@Entity
@Table(name = "KURS")                                  // Hibernate bildet die Klasse auf die Tabelle KURS ab
public class Kurs {
    @Id @GeneratedValue
    private Long id;
    private String titel;
    private LocalDate start;
    private int plaetze;
    @OneToMany(mappedBy = "kurs")
    private List<Buchung> buchungen = new ArrayList<>();
    // Getter und Setter …
}

@Stateless
public class KursDac {
    @PersistenceContext private EntityManager em;      // vom Container bereitgestellt
    public List<Kurs> freie() {
        return em.createQuery("SELECT k FROM Kurs k WHERE SIZE(k.buchungen) < k.plaetze", Kurs.class)
                 .getResultList();                     // JPQL, der ORM-Provider erzeugt SQL
    }
}

Merke: Web Container und EJB Container sind Pakete, keine Komponenten. Zwischen ihnen braucht es keinen Web Service: Java spricht mit Java über RMI. Session Beans tragen «EJB», Message-Driven Beans «EJB MDB».

    Schritt 9 · Persistence/Data Tier

    Arten von Datenbanken

    Im Persistence Tier liegen die Daten in einem Datenbankmanagementsystem (DBMS). Welche Art passt, hängt von der Struktur der Daten, den Konsistenzanforderungen und der Last ab. Im Diagramm zeichnest du die Datenbank als Komponente «DB in <Produkt>», den DBMS-Server nicht.

    SQL: relationales DBMS

    Tabellen mit festem Schema, Beziehungen über Schlüssel, Abfragen in SQL, Transaktionen nach ACID.

    PostgreSQL, MySQL, SQL Server, Oracle · für Verträge, Buchhaltung, Bestellungen

    NewSQL

    SQL und ACID wie ein RDBMS, aber horizontal über viele Knoten verteilt (Sharding und Replikation automatisch).

    Schritt 10 · CRUD, CQRS und Event Sourcing

    Lesen und Schreiben trennen, Ereignisse speichern

    CRUD (Create, Read, Update, Delete) nutzt ein einziges Datenmodell für Lesen und Schreiben. Das ist einfach und passt für die meisten Anwendungen. Wird aber sehr viel mehr gelesen als geschrieben, oder brauchen Lesen und Schreiben ganz andere Strukturen, stösst ein gemeinsames Modell an Grenzen.

    CQRS (Command Query Responsibility Segregation) trennt die beiden Seiten. Commands ändern den Zustand und gehen ans Schreibmodell, Queries lesen nur und gehen ans Lesemodell. Das Lesemodell ist eine eigene, fürs Lesen optimierte Datenbank (z. B. fertige Listen als Dokumente), die nach jeder Änderung nachgeführt wird, oft asynchron über Events. Folge: Die Lese-Seite ist für kurze Zeit «schliesslich konsistent».

    Ausprobieren

    Bedeutung für die Skalierung

    Eine Datenbank-Instanz schafft hier 2 000 Zugriffe pro Sekunde. Stell die Last ein. Bei CRUD trägt eine Datenbank alles. Bei CQRS trägt die Schreib-DB nur die Commands, die Lese-Seite lässt sich mit Replikaten beliebig verbreitern.

    Event Sourcing (ES) speichert nicht den aktuellen Zustand, sondern jede Zustandsänderung als Ereignis in einem Event Store, der nur anhängt (append-only). Den aktuellen Zustand berechnest du, indem du die Events der Reihe nach abspielst (Replay). Projektionen halten fertige Lesemodelle bereit, darum kommt ES oft zusammen mit CQRS vor. Vorteile: lückenlose Historie, Zeitreise, neue Auswertungen nachträglich. Nachteile: mehr Komplexität, Events nie mehr ändern, Korrekturen nur als neues Event.

    Ausprobieren

    Event Store eines Velo-Guthabens

    Löse Commands aus. Jedes erzeugt ein Event, das hinten angehängt wird. Mit dem Schieber reist du in der Zeit zurück: Der Zustand entsteht nur aus den Events bis zu diesem Punkt. Ein Fehler wird nicht gelöscht, sondern mit einem Gegen-Event korrigiert.

      Schritt 11 · Mikroarchitektur

      Ein skriptbasierter Microservice von innen

      In der Makroarchitektur ist ein Microservice eine einzige Komponente «Microservice». Seine Mikroarchitektur zeigt, was darin steckt: dieselben Schichten wie im Monolithen, nur für ein Fachgebiet und mit eigener Persistenz. Das Beispiel ist der Dienst «Ausleihe» eines Velo-Verleihs (fiktiv) in Node.js: REST nach aussen, Events über den Broker, eine Dokument-DB für die eigenen Daten und eine Key-Value-DB als Cache.

      Merke: Der Microservice besitzt seine Daten allein (database per service). Andere Dienste fragen über die API oder lesen Events, nie direkt in seiner Datenbank. Die Cache-DB beschleunigt das Lesen; fällt sie aus, liest der Dienst langsamer direkt aus der Dokument-DB.

      Auftrag 1 lösen: Checkliste und Fallen

      Checkliste

      1. Auftrag lesen: Welcher Stack ist vorgegeben oder zu wählen? Welche Clients, Fachkomponenten, Consumer, Provider und Nachrichten nennt der Text?

      2. Stack wählen und begründen: rund fünf Sätze mit Vor- und Nachteilen, allgemein und für den Fall.

      3. Pakete anlegen wie in der Referenz: Client Tier, Middle Tier mit Web Tier und Business Tier (Facade, Business Logic, Async, Data Access, Service Access), Data Tier; rechts Consumer, MOM, Provider. Middleware im Paketnamen (IIS, node.js, Web und EJB Container).

      4. Komponenten einzeichnen: Business-Komponenten einzeln (je Fachgebiet), Receiver und Sender getrennt, je Provider ein Adapter, alle Umsysteme konkret.

      5. Stereotypen setzen: «JS», «C#», «ASP.NET», «EJB», «EJB MDB». Clients, Datenbanken und Umsysteme brauchen keinen.

      6. Schnittstellen und Verbindungen: Bälle für angebotene APIs (HTTP, REST, SOAP, Business API, RMI, AMQP, JMS), jede Assoziation mit Protokoll und Format beschriften.

      7. Beschreibungen: 2 bis 3 Sätze je Komponente und Paket: was es ist, was es tut, warum diese Technologie.

      Falle 1: In der Referenz heisst es «Business Components» (Plural, zusammengefasst). Im konkreten Fall zeichnest du jede fachliche Komponente einzeln, z. B. Kurse, Buchungen, Kundinnen.

      Falle 2: Ein gemeinsamer Adapter für alle Provider gibt Abzug. Je Service Provider ein eigener Adapter im Service Access Layer, mit eigener Verbindung zum Provider.

      Falle 3: Receiver und Sender sind zwei Komponenten im Async Communication Layer. Eine einzelne «Async-Komponente» reicht im konkreten Fall nicht.

      Falle 4: Web-Server (IIS, Nginx, Apache), Application Server (WildFly), DBMS-Server und Security-Server sind Infrastruktur. Keine Komponente, höchstens im Paketnamen.

      Falle 5: API-Gateway und Integration Middleware gehören nicht in die Mehrschichtenarchitektur. Der Message Broker schon: Er steht im Paket MOM.

      Falle 6: In Jakarta EE ruft der Web Container die Facade per RMI auf, nicht per REST. In .NET und skriptbasiert läuft der Zugang zum Business Tier über REST oder gRPC.

      Beschreibungen schreiben: die Drei-Satz-Formel

      1. Was ist es und wo liegt es? 2. Was tut es (Aufgabe, Schnittstellen)? 3. Warum so (Technologie, Vorteil)? Beispiel für eine Facade in .NET:

      «Die Business API ist die Business Facade und der einzige Zugang zum Business Tier. Sie bietet die Fachfunktionen über REST an und leitet jeden Aufruf an die zuständige Business-Komponente weiter. So lassen sich Web Tier und Business Tier auf getrennten Servern betreiben und unabhängig skalieren.»

      Auf einen Blick

      • Der Server nimmt Anfragen an, liefert Seiten oder Daten, führt die Geschäftslogik aus, speichert konsistent und integriert Umsysteme als Provider und Consumer.
      • Bauplan aller drei Referenzen: Web Tier (Presentation Services, Web API) → Business Tier (Facade, Business Components, Driven Adapters: Data Access, Async, Service Access) → Data Tier; rechts Consumer, MOM, Provider.
      • Stereotypen: skriptbasiert «JS»/«PHP», .NET «ASP.NET» für Präsentation und «C#» für den Rest, Jakarta «EJB» für Session Beans und «EJB MDB» für Receiver und Sender.
      • Zugang zum Business Tier: Facade mit REST oder gRPC (.NET, skriptbasiert), mit RMI (Jakarta EE). DACs: mongoose, Entity Framework, JPA.
      • Im konkreten Fall: Business-Komponenten einzeln, Receiver und Sender getrennt, je Provider ein Adapter, keine Web-, Application- oder DBMS-Server als Komponente.
      • Persistenz: RDBMS (ACID), NewSQL (SQL verteilt), NoSQL (Dokument, Key-Value), objektorientiert. CQRS trennt Schreib- und Lesemodell und skaliert die Lese-Seite; Event Sourcing speichert Ereignisse und berechnet den Zustand per Replay.
