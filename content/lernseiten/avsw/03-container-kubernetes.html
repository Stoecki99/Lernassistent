AVSW · Thema 3 · Container und Kubernetes

Container und Kubernetes

Microservices sind schön, aber jemand muss sie auch betreiben: auf vielen Rechnern, in vielen Kopien, ohne nachts aufzustehen. Hier lernst du, wie du eine Anwendung mit Docker in ein Image packst und wie Kubernetes daraus einen Betrieb macht, der sich selbst repariert. Am Schluss übersetzt du Anforderungstexte und YAML-Dateien in ein Kubernetes-Bild.

Hinweis: Eigene Beispiele und Lösungen, nicht vom Dozenten bestätigt. Begriffe und Notation mit den Vorlesungsfolien abgleichen.
Nach dieser Station kannst du:
  • VM und Container unterscheiden und erklären, was Image, Layer, Container und Registry sind,
  • ein mehrstufiges Dockerfile und eine docker-compose.yml lesen und schreiben,
  • Control Plane und Worker Nodes eines Kubernetes-Clusters beschreiben,
  • für ein Problem das passende Kubernetes-Objekt wählen: Pod, Deployment, Service, Ingress, ConfigMap, Secret, PVC, StatefulSet, HPA,
  • aus einem Anforderungstext oder YAML ein Kubernetes-Bild modellieren.

Schritt 0 · Ohne Vorwissen

Die fünf Bausteine dieser Station

Stell dir den Webshop «Gipfel» vor, der Wanderschuhe verkauft. Sein Code liegt im Git-Repository. Damit Kundinnen einkaufen können, muss dieser Code irgendwo laufen, und zwar zuverlässig. Dafür brauchst du fünf Begriffe. Lies die Karten von links nach rechts: Jede baut auf der vorherigen auf.

Image = Bauplangipfel/shop:1.4.2

Ein fertig gepacktes, unveränderliches Paket: dein Code, die Java-Laufzeit, alle Bibliotheken. Wie eine Klasse in Java: Sie beschreibt, läuft aber selbst nicht.

Container = laufende Kopiedocker run gipfel/shop:1.4.2

Ein gestartetes Image, wie ein Objekt aus der Klasse. Aus einem Image startest du beliebig viele Container. Jeder ist vom Rest des Rechners abgeschirmt.

Pod = Wohnungshop-web-7f9c-k2x4

Die kleinste Einheit, die Kubernetes startet. Wie eine WG: ein oder wenige Container teilen sich Adresse (IP) und Abstellraum (Volumes).

Deployment = Schichtleitungreplicas: 3

Sorgt dafür, dass immer genau so viele Pods laufen wie bestellt. Fällt einer aus, startet es Ersatz. Wie eine Schichtleiterin, die bei einer Krankmeldung sofort jemanden einteilt.

Service = Telefonzentraleshop-web:80

Eine feste Adresse vor wechselnden Pods. Wie die Hauptnummer eines Spitals: Du rufst immer dieselbe Nummer an und wirst mit einer freien Person verbunden.

Kurz üben: Welcher Baustein ist gemeint?

Frag dich: Ist es ein Bauplan, ein laufender Prozess, eine Hülle für Container, ein Auftrag «halte X am Laufen» oder eine feste Adresse?

Schritt 2 · Von der YAML-Datei zum Bild

YAML Zeile für Zeile in ein Bild übersetzen

In Kubernetes beschreibst du alles in YAML-Dateien. Das Kubernetes-Bild ist dieselbe Information als Zeichnung. Klick dich mit «Weiter» durch. Fahre über eine unterstrichene YAML-Stelle oder tippe darauf: Der passende Teil im Bild leuchtet auf, und umgekehrt.

Bis jetzt laufen drei Pods, aber niemand erreicht sie. Die zweite Datei baut den Weg von aussen bis zu den Pods.

Schritt 3 · Das Verfahren

So zeichnest du jedes Kubernetes-Bild

Egal ob die Aufgabe ein Anforderungstext oder eine YAML-Datei ist: Du gehst immer gleich vor. Substantive werden Bausteine, Verben werden Verbindungen.

  1. Einstieg suchen. Steht da eine Domain oder ein Pfad («unter shop.gipfel.ch»)? Dann beginnt der Weg beim Ingress.
  2. Laufende Teile finden. Jede Anwendung wird zu Pods. Zustandslos (Web, API) → Deployment. Mit eigenen Daten (Datenbank) → StatefulSet.
  3. Services davor setzen. Wer Pods anspricht, spricht einen Service an. Der Service findet die Pods über den Label-Selector.
  4. Konfiguration zuordnen. Nicht geheim → ConfigMap. Geheim (Passwort, Token, Schlüssel) → Secret. Pfeil «liest Konfig/Secret» vom Pod zur Quelle.
  5. Daten sichern. Was einen Neustart überleben muss → PersistentVolumeClaim. Pfeil «speichert in».
  6. Kontrollieren. Eine Anfrage von aussen bis zur Datenbank nachfahren. Alles, was im Text nicht vorkommt, fliegt raus.

Falle 1: Der Service findet Pods nicht über den Namen des Deployments. Er sucht ausschliesslich über Labels. Heisst das Deployment shop-web, tragen die Pods aber das Label app: shop, dann muss der Selector app: shop lauten. Ein Tippfehler im Label und der Service hat keine Ziele: Anfragen enden mit Fehler 503.
Falle 2: Einzelne Pods von Hand anlegen. Einen Pod, den du direkt mit kind: Pod erzeugst, startet niemand neu, wenn er verschwindet. Für Self-Healing brauchst du immer ein Deployment oder StatefulSet darüber.
Falle 3: Daten im Container speichern. Die beschreibbare Schicht eines Containers verschwindet mit ihm. Eine Datenbank ohne PVC ist nach jedem Neustart leer.
Warum zeigt der Pfeil vom Pod zur ConfigMap und nicht umgekehrt?

Die ConfigMap ist passiv. Sie schickt nichts. Beim Start des Pods holt das kubelet die Werte und setzt sie als Umgebungsvariablen oder Dateien in den Container. Der Pod ist also der aktive Teil, der «liest».

Dasselbe gilt für «speichert in»: Der Pod schreibt in den PVC, nicht der PVC in den Pod.

Deployment oder StatefulSet: Wie entscheide ich?

Frag: Ist es egal, welcher Pod eine Anfrage bekommt, und darf jeder Pod jederzeit durch einen neuen ersetzt werden? Dann Deployment. Typisch: Web-Frontend, REST-API, Worker.

Braucht jeder Pod seinen eigenen, festen Speicher und einen festen Namen (zum Beispiel Primär- und Replikat-Datenbank)? Dann StatefulSet. Die Pods heissen dann shop-db-0, shop-db-1, und jeder bekommt seinen eigenen PVC.

Schritt 4 · Container mit Docker

Container: abgeschirmte Prozesse statt ganzer Rechner

Früher lief jede Anwendung auf eigenem Server oder in einer eigenen virtuellen Maschine (VM). Eine VM bringt ein komplettes Betriebssystem mit eigenem Kernel mit. Das ist sicher abgeschottet, aber schwer: Gigabytes gross, Start in Minuten. Ein Container teilt sich dagegen den Kernel des Host-Betriebssystems. Er bringt nur die Anwendung und ihre Bibliotheken mit. Der Linux-Kernel schirmt ihn ab (Namespaces für die Sicht, cgroups für CPU und Speicher).

Falle: «Ein Container ist eine kleine VM.» Nein. Ein Container hat keinen eigenen Kernel. Darum startet er in Sekunden, darum läuft ein Linux-Container nicht direkt auf einem Windows-Kernel, und darum ist die Abschottung schwächer als bei einer VM. In der Cloud laufen Container meist in VMs: Die Worker Nodes sind VMs.

Image, Layer, Container

Ein Image besteht aus übereinandergelegten Layern. Jede Anweisung im Dockerfile, die Dateien ändert, legt einen neuen Layer darüber. Layer sind nur lesbar und werden geteilt: Zehn Container aus demselben Image brauchen die Java-Laufzeit nur einmal auf der Festplatte. Jeder Container bekommt obendrauf eine eigene, dünne beschreibbare Schicht. Wird der Container gelöscht, ist diese Schicht weg.

Container 1: beschreibbare Schicht (Logs, temporäre Dateien)Container 2: beschreibbare Schicht
Image ghcr.io/gipfel/shop:1.4.2 · nur lesen · von beiden geteilt Layer 4: COPY --from=build … app.jarca. 45 MB, ändert sich bei jedem Build Layer 3: RUN useradd --system shopwenige kB Layer 2: WORKDIR /appleer Layer 1: Basis eclipse-temurin:21-jreca. 200 MB, kommt aus dem Cache
Tipp: Docker baut nur Layer neu, die sich ab einer Änderung unterscheiden. Darum kopierst du zuerst die Abhängigkeitsliste (pom.xml, package.json) und erst danach den Quellcode. Dann kommen die Bibliotheken bei einer kleinen Code-Änderung aus dem Cache, und der Build dauert Sekunden statt Minuten.

Vom Code zum laufenden Container

  1. Code + Dockerfile
  2. → docker build
  3. Image
  4. → docker push
  5. Registry
  6. → pull
  7. Server / Node
  8. → run
  9. Container

In der Praxis baut die CI-Pipeline (GitHub Actions, GitLab CI) bei jedem Merge das Image und schiebt es in die Registry. Der Server baut nichts selbst, er holt nur fertige Images.

Dockerfile mit zwei Stufen (multi-stage)

Zum Bauen brauchst du JDK, Maven und den Quellcode. Zum Ausführen brauchst du nur eine Java-Laufzeit und die fertige JAR-Datei. Ein mehrstufiges Dockerfile trennt das: Stufe 1 baut, Stufe 2 übernimmt nur das Ergebnis. Das Endimage ist kleiner und enthält keine Build-Werkzeuge, die ein Angreifer nutzen könnte.

# Stufe 1: bauen (JDK und Maven, wird später weggeworfen)
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline      # Abhängigkeiten: eigener Layer, meist aus dem Cache
COPY src ./src
RUN mvn -q package -DskipTests

# Stufe 2: ausführen (nur JRE, kein Maven, kein Quellcode)
FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd --system shop
COPY --from=build /src/target/shop.jar app.jar
USER shop                            # nicht als root laufen
EXPOSE 8080
ENV SPRING_PROFILES_ACTIVE=prod
ENTRYPOINT ["java", "-jar", "app.jar"]

Mehrere Container zusammen: Docker Compose

Für die Entwicklung willst du Shop und Datenbank mit einem Befehl starten. docker compose up liest dafür eine YAML-Datei. Die Container finden sich über ihren Dienstnamen: Der Shop erreicht die Datenbank unter dem Hostnamen db.

services:

      - db

    environment:
      POSTGRES_DB: shop
      POSTGRES_PASSWORD: ${DB_PASSWORD}

  db-daten:
Compose oder Kubernetes? Compose startet Container auf einem Rechner. Fällt der Rechner aus, steht alles. Kubernetes verteilt Container auf viele Rechner, ersetzt ausgefallene und skaliert. Compose für die Entwicklung, Kubernetes für den Betrieb.

Warum ist ein Warenkorb im Arbeitsspeicher des Pods ein Problem?

Der Service verteilt Anfragen auf drei Pods. Legt Anna den Schuh bei Pod 1 in den Warenkorb und landet die nächste Anfrage bei Pod 2, ist der Warenkorb leer. Und wird Pod 1 ersetzt, ist der Warenkorb ganz weg.

Darum: Pods zustandslos halten, Zustand in eine Datenbank oder einen Cache. Dann ist es egal, welcher Pod antwortet.

Schritt 5 · Kubernetes-Architektur

Ein Cluster, der sich selbst repariert

Kubernetes (kurz K8s) verteilt Container auf viele Rechner. Du sagst nicht «starte Container X auf Server 3», sondern du beschreibst den gewünschten Zustand: «Vom Shop sollen drei Pods laufen.» Kubernetes sorgt dafür, dass es so ist und so bleibt.

Control Plane: das Gehirn

  • API-Server: die einzige Tür. kubectl, Controller und kubelets reden nur mit ihm.
  • etcd: speichert den gesamten Zustand, also Soll und gemeldetes Ist.
  • Scheduler: wählt für jeden neuen Pod eine Node mit genug Platz.
  • Controller Manager: viele Kontrollschleifen, zum Beispiel der ReplicaSet-Controller, der Pods nachzählt.

Worker Nodes: die Hände

  • kubelet: Agent auf jeder Node. Startet die Container der zugeteilten Pods, prüft die Probes, meldet den Zustand.
  • Container-Runtime: zum Beispiel containerd. Holt Images und startet Container.
  • kube-proxy: setzt die Netzwerkregeln, damit Service-Adressen bei den Pods ankommen.

Deklarativ statt imperativ: der Soll-Ist-Abgleich

Imperativ heisst: Du gibst Befehle («starte», «stoppe»). Deklarativ heisst: Du beschreibst das Ziel, und das System findet den Weg. Kubernetes arbeitet deklarativ. Jeder Controller läuft in einer Endlosschleife:

  1. 1 · Ist beobachten
    «2 Pods laufen»
  2. →
  3. 2 · mit Soll vergleichen
    «3 bestellt»
  4. →
  5. 3 · handeln
    «1 Pod erstellen»
  6. ↺ von vorn

Daraus folgt das Self-Healing: Verschwindet ein Pod, ist Ist kleiner als Soll, und der Controller erstellt einen neuen. Du musst nichts tun. Probier es im Labor aus.

Labor: Pods abstürzen lassen und skalieren

Deployment web auf zwei Worker Nodes, höchstens drei Pods pro Node. Grün umrandet: bereit. Gestrichelt: startet, die Readiness-Probe ist noch nicht grün. Der Service schickt Anfragen nur an bereite Pods (Pfeile).

3

Entspricht: kubectl scale deployment/web --replicas=3

    Genau genommen: Stürzt nur der Prozess im Container ab, startet das kubelet den Container im selben Pod neu (in kubectl get pods steigt die Spalte RESTARTS). Verschwindet der ganze Pod (gelöscht, Node weg, zu wenig Speicher), ersetzt ihn der ReplicaSet-Controller durch einen neuen Pod mit neuem Namen. Bei einem Node-Ausfall wartet Kubernetes in Wirklichkeit einige Minuten, bevor es Ersatz startet. Im Labor geht es schneller.
    # imperativ: Befehle, der Zustand steht nirgends in einer Datei
kubectl create deployment web --image=ghcr.io/gipfel/shop:1.4.2
kubectl scale deployment/web --replicas=4

# deklarativ: Soll-Zustand in Dateien (im Git), beliebig oft anwendbar
kubectl apply -f k8s/
kubectl diff -f k8s/        # zeigt, was apply ändern würde
    Falle: imperativ und deklarativ mischen. Skalierst du mit kubectl scale auf 4 Pods und steht in der YAML-Datei replicas: 3, setzt das nächste kubectl apply wieder auf 3 zurück. Die Datei im Git ist die Wahrheit. Darum ändern Teams den Cluster nur über Dateien (GitOps mit Werkzeugen wie Argo CD oder Flux).
    Schritt 6 · Die wichtigsten Objekte mit Code

    Pod, Deployment, Service, Ingress und Co.

    Jedes Objekt hat dieselbe Grundform: apiVersion (welche Schnittstelle), kind (welche Art Objekt), metadata (Name, Namespace, Labels) und spec (der Soll-Zustand). Kubernetes ergänzt selbst status (der Ist-Zustand).

    Deployment mit Probes und Ressourcen

    So sieht ein vollständiges Deployment für den Gipfel-Shop aus. Es legt ein ReplicaSet an, und das ReplicaSet legt die drei Pods an.

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-web
  namespace: shop
spec:
  replicas: 3                           # Soll: drei Pods
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  selector:
    matchLabels: { app: shop }           # welche Pods gehören mir?
  template:                              # Vorlage für jeden Pod
    metadata:
      labels: { app: shop }
    spec:
      containers:
        - name: shop
          image: ghcr.io/gipfel/shop:1.4.2
          ports: [{ containerPort: 8080 }]
          envFrom:
            - configMapRef: { name: shop-config }
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef: { name: db-zugang, key: password }
          resources:
            requests: { cpu: 250m, memory: 512Mi }   # reserviert, zählt für den Scheduler
            limits: { memory: 768Mi }                 # mehr = Container wird beendet
          readinessProbe:                  # bereit für Anfragen?
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            periodSeconds: 5
          livenessProbe:                   # lebt er noch?
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            initialDelaySeconds: 30
            periodSeconds: 10

    Probes: Liveness, Readiness, Startup

    ProbeFrageWenn sie fehlschlägtBeispiel
    ReadinessKann der Pod jetzt Anfragen annehmen?Der Service nimmt ihn aus der Verteilung. Kein Neustart.Spring Boot lädt noch den Produktkatalog
    LivenessLebt der Prozess noch sinnvoll?Das kubelet startet den Container neu.Deadlock: Prozess läuft, antwortet aber nie
    StartupIst der langsame Start fertig?Bis sie grün ist, ruhen die anderen Probes.Alte Java-Anwendung braucht 2 Minuten
    Falle: Liveness und Readiness verwechseln. Prüft die Liveness-Probe die Datenbank und ist die Datenbank kurz weg, startet Kubernetes alle Shop-Pods neu. Das hilft nicht und macht es schlimmer. Abhängigkeiten gehören höchstens in die Readiness-Probe. Die Liveness-Probe prüft nur: Lebt mein eigener Prozess?

    Rolling Update und Rollback

    Änderst du im Deployment das Image auf 1.5.0, legt Kubernetes ein neues ReplicaSet an und tauscht die Pods schrittweise aus. Mit maxSurge: 1 darf kurz ein Pod mehr laufen, mit maxUnavailable: 0 sind nie weniger als drei bereit. Kundinnen merken nichts.

    Start1.4.21.4.21.4.2
    Schritt 11.4.21.4.21.4.21.5.0 startetNeuer Pod startet zusätzlich (maxSurge 1).
    Schritt 21.4.21.4.21.4.21.5.0Erst wenn er bereit ist (Readiness), wird ein alter beendet.
    Schritt 31.4.21.4.21.5.01.5.0Dasselbe Spiel, bis alle neu sind.
    Ende1.5.01.5.01.5.0Das alte ReplicaSet bleibt mit 0 Pods stehen: Daraus macht Kubernetes einen Rollback.
    kubectl set image deployment/shop-web shop=ghcr.io/gipfel/shop:1.5.0
kubectl rollout status deployment/shop-web     # Fortschritt verfolgen
kubectl rollout history deployment/shop-web    # Versionen anzeigen
kubectl rollout undo deployment/shop-web       # zurück auf 1.4.2
    Tipp: Schreib in der Praxis die neue Version in die YAML-Datei und mach kubectl apply. kubectl set image ist imperativ und weicht vom Git-Stand ab. Und: Nutze nie :latest. Mit einem festen Tag weisst du, welche Version läuft, und ein Rollback hat ein klares Ziel.

    Service: feste Adresse vor wechselnden Pods

    Pods kommen und gehen, und jeder neue Pod hat eine neue IP-Adresse. Der Service gibt dir eine feste Adresse und einen DNS-Namen. Innerhalb des Namespaces erreichst du ihn einfach unter shop-web, von überall unter shop-web.shop.svc.cluster.local. Welche Pods dahinter stehen, bestimmt nur der Label-Selector.

    apiVersion: v1
kind: Service
metadata:
  name: shop-web
  namespace: shop
spec:
  type: ClusterIP                # Standard: nur im Cluster erreichbar
  selector:
    app: shop                    # alle Pods mit diesem Label
  ports:
    - port: 80                   # an diesem Port hört der Service
      targetPort: 8080           # an diesen Port im Container leitet er weiter
    TypErreichbar vonTypischer Einsatz
    ClusterIPnur innerhalb des ClustersDatenbank, interne APIs (Bestellservice ruft Lagerservice)
    NodePortjede Node an einem festen Port (30000 bis 32767)Tests, kleine Installationen ohne Cloud
    LoadBalancerInternet über einen Load Balancer der Cloud mit eigener IPein einzelner Dienst nach aussen, auch Nicht-HTTP (z. B. MQTT)

    Ingress: ein Eingang für viele Services

    Ein LoadBalancer pro Dienst wird teuer. Ein Ingress ist eine Liste von HTTP-Regeln: Welcher Host und welcher Pfad geht an welchen Service. Ausgeführt werden die Regeln von einem Ingress-Controller (zum Beispiel NGINX oder Traefik), der selbst als Pod im Cluster läuft. Er übernimmt auch HTTPS.

    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: gipfel
  namespace: shop
spec:
  tls:
    - hosts: [shop.gipfel.ch]
      secretName: gipfel-tls             # Zertifikat liegt in einem Secret
  rules:
    - host: shop.gipfel.ch
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: shop-api, port: { number: 80 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: shop-web, port: { number: 80 } }

    ConfigMap und Secret: Konfiguration ausserhalb des Images

    Dasselbe Image läuft in dev und prod. Was sich unterscheidet, steht in einer ConfigMap (nicht geheim) oder in einem Secret (geheim). Der Pod liest beides beim Start als Umgebungsvariablen oder als Dateien.

    apiVersion: v1
kind: ConfigMap
metadata: { name: shop-config, namespace: shop }
data:
  WAEHRUNG: "CHF"
  LOG_LEVEL: "INFO"
  DB_URL: "jdbc:postgresql://shop-db:5432/shop"
---
apiVersion: v1
kind: Secret
metadata: { name: db-zugang, namespace: shop }
type: Opaque
stringData:                      # Kubernetes speichert es Base64-codiert
  password: "bitte-nicht-ins-git"
    Falle: «Secret = verschlüsselt». Ein Secret ist nur Base64-codiert. Wer das Objekt lesen darf, liest das Passwort. Schütze Secrets mit Zugriffsrechten (RBAC), schalte die Verschlüsselung in etcd ein und lege sie nie unverschlüsselt ins Git. Dafür gibt es Werkzeuge wie Sealed Secrets oder einen externen Tresor wie HashiCorp Vault.

    Daten, die bleiben: Volume, PVC und StatefulSet

    Ein PersistentVolumeClaim ist eine Bestellung: «Ich brauche 10 GiB Speicher, den ein Pod beschreiben darf.» Der Cluster liefert dazu ein PersistentVolume, in der Cloud zum Beispiel eine Netzwerk-Festplatte. Wird der Pod ersetzt, hängt Kubernetes denselben Speicher beim neuen Pod ein. Für Datenbanken nimmst du ein StatefulSet: Es gibt jedem Pod einen festen Namen und mit volumeClaimTemplates einen eigenen PVC.

    apiVersion: apps/v1
kind: StatefulSet
metadata: { name: shop-db, namespace: shop }
spec:
  serviceName: shop-db
  replicas: 1                       # Pod heisst shop-db-0
  selector: { matchLabels: { app: shop-db } }
  template:
    metadata: { labels: { app: shop-db } }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          env:
            - name: POSTGRES_PASSWORD
              valueFrom: { secretKeyRef: { name: db-zugang, key: password } }
          volumeMounts:
            - { name: db-daten, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:             # je Pod ein eigener PVC: db-daten-shop-db-0
    - metadata: { name: db-daten }
      spec:
        accessModes: [ReadWriteOnce]
        resources: { requests: { storage: 10Gi } }

    Namespace: Ordnung im Cluster

    Ein Namespace trennt Objekte: Im Namespace dev und im Namespace prod darf es je einen Service shop-web geben. Pro Namespace vergibst du Rechte («Team Shop darf nur in shop ändern») und Kontingente («höchstens 8 CPU»). Ein Namespace ist keine Netzwerk-Sperre: Ohne NetworkPolicy dürfen Pods über Namespace-Grenzen hinweg reden.

    HorizontalPodAutoscaler: Pods nach Last

    Am Black Friday reicht ein Shop-Pod nicht. Der HPA misst regelmässig die Auslastung (zum Beispiel CPU im Verhältnis zu requests) und passt replicas an. Die Grundformel lautet:

    $$\text{Pods}_{\text{neu}} = \left\lceil \text{Pods}_{\text{jetzt}} \cdot \frac{\text{Auslastung}_{\text{jetzt}}}{\text{Auslastung}_{\text{Ziel}}} \right\rceil$$

    Beispiel: 3 Pods, 140 % CPU, Ziel 70 %: \(\lceil 3 \cdot 140 / 70 \rceil = 6\) Pods. Begrenzt durch minReplicas und maxReplicas.

    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: shop-web, namespace: shop }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: shop-web }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
    Merke: Der HPA skaliert horizontal, also mehr Pods. Das klappt nur mit zustandslosen Pods. Eine Datenbank skalierst du so nicht. «Vertikal» hiesse: einem Pod mehr CPU und Speicher geben.

    kubectl: die wichtigsten Befehle

    kubectl apply -f k8s/                         # Soll-Zustand anwenden (deklarativ)
kubectl get pods -n shop -o wide             # Pods mit Node und IP
kubectl get deploy,svc,ingress -n shop
kubectl describe pod shop-web-7f9c-k2x4 -n shop  # Ereignisse: warum Pending, warum Neustart?
kubectl logs -f deploy/shop-web -n shop       # Logs (stdout) mitlesen
kubectl get endpoints shop-web -n shop        # welche Pod-IPs stehen hinter dem Service?
kubectl port-forward svc/shop-web 8080:80 -n shop  # lokal testen ohne Ingress
kubectl delete pod shop-web-7f9c-k2x4 -n shop # Self-Healing beobachten

    Helm: YAML als Paket

    Für dev, test und prod brauchst du fast dieselben YAML-Dateien, nur mit anderen Werten (Replicas, Domain, Image-Tag). Helm macht daraus ein Chart: Vorlagen mit Platzhaltern und eine Datei values.yaml mit den Werten. Ein Befehl installiert oder aktualisiert alles zusammen und kann auch zurückrollen.

    spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: shop
          image: "{{ .Values.image.repo }}:{{ .Values.image.tag }}"
    replicaCount: 3
image:
  repo: ghcr.io/gipfel/shop
  tag: "1.4.2"
ingress:
  host: shop.gipfel.ch
    helm install shop ./shop-chart -n shop -f values-prod.yaml
helm upgrade shop ./shop-chart -n shop -f values-prod.yaml --set image.tag=1.5.0
helm rollback shop 1 -n shop

    Sitzt es?

    Das Wichtigste auf einen Blick

    • Image = unveränderlicher Bauplan aus Layern, Container = laufende Instanz. Container teilen sich den Kernel des Hosts, VMs nicht.
    • Mehrstufiges Dockerfile: eine Stufe baut, die letzte Stufe enthält nur Laufzeit und Ergebnis. Images immer mit festem Tag, nie :latest.
    • Kubernetes ist deklarativ: Du beschreibst das Soll, Controller gleichen laufend mit dem Ist ab. Daraus entsteht Self-Healing.
    • Anfrageweg: Ingress (Host, Pfad) → Service (feste Adresse, Label-Selector) → Pods eines Deployments.
    • Konfiguration und Daten: ConfigMap für Einstellungen, Secret für Geheimes (nur Base64), PVC für Daten, StatefulSet für Datenbanken.
    • Readiness entscheidet über Traffic, Liveness über Neustart. Der HPA passt die Anzahl Pods an die Last an.
